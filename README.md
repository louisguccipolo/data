# Capibara — хранилище данных маркетплейса

ELT-хранилище на данных Olist для анализа заказов, продаж, платежей и доставки.
Восемь исходных таблиц преобразуются в историческую интеграционную модель
Data Vault, затем — в звезду и 11 витрин для аналитики и BI.

**Модель и пайплайн:**

- **ODS:** 35 таблиц Data Vault — хабы, линки, история атрибутов и активности связей.
- **DDS:** 7 измерений, 4 факта с разным зерном, исторические версии и привязка
  продажи к категории и адресу на момент наблюдения заказа.
- **Пайплайн:** инкрементальный EL, снимки ключей, обработка изменений схемы,
  dbt-модели и тесты, проверяемая публикация 11 витрин в ClickHouse.

Правила очистки, историчности и расчёта показателей определяются в dbt.
Airflow управляет единой цепочкой загрузки, сборки, проверок и публикации.

**Стек:** PostgreSQL 16 · dbt · Airflow 3 · ClickHouse · Docker Compose.

## Схема решения

```mermaid
flowchart LR
    SOURCE["Olist<br/>8 таблиц"] --> RAW["raw<br/>История загрузок"]
    RAW -->|staging| ODS["ODS<br/>Data Vault"]
    ODS --> DDS["DDS<br/>Звезда"]
    DDS --> MART["mart<br/>11 витрин"]
    MART --> CH["ClickHouse<br/>Данные для BI"]
```

PostgreSQL хранит исходные наблюдения, ODS, DDS и витрины. dbt выполняет
преобразования от staging до mart; Airflow запускает всю цепочку.
ClickHouse обслуживает BI-запросы, Superset подключается к нему отдельно.

## ODS: интеграционная модель Data Vault

ODS сохраняет бизнес-ключи, связи и все наблюдавшиеся изменения источников.
Слой состоит из **7 хабов, 5 линков, 9 сателлитов атрибутов, 5 сателлитов
присутствия, 8 моделей активности и журнала ошибок приведения типов**.
Это 34 инкрементальные модели с добавлением строк и таблица `err_cast`.

Перед ODS работают 13 staging-view: восемь таблиц источника и пять снимков
ключей. Здесь выполняются приведение типов, нормализация ключей и расчёт
хешей; бизнес-интерпретация данных относится к DDS.

### Сущности и ключи

| Хаб | Бизнес-ключ | Что представляет |
|---|---|---|
| `hub_order` | `order_id` | Заказ |
| `hub_customer` | `customer_unique_id` | Постоянный покупатель |
| `hub_customer_profile` | `customer_id` | Профиль покупателя, связанный с заказом |
| `hub_product` | `product_id` | Товар |
| `hub_seller` | `seller_id` | Продавец |
| `hub_category` | `product_category_name` | Категория товара |
| `hub_review` | `review_id` | Отзыв |

Разделение покупателя и профиля принципиально: повторные покупки считаются
по `customer_unique_id`, а адрес хранится у профиля заказа. Хаб пополняется
из каждой таблицы, где встречается его ключ; источники при загрузке Vault
не соединяются между собой. Это сохраняет поздние и неполные сущности.

### Связи

| Линк | Участники и зерно |
|---|---|
| `link_order_profile` | Заказ ↔ профиль; связь берётся из orders |
| `link_customer_profile` | Профиль ↔ постоянный покупатель; связь берётся из customers |
| `link_order_item` | Заказ × товар × продавец с зависимым ключом `order_item_id` |
| `link_product_category` | Товар ↔ категория |
| `link_order_review` | Заказ ↔ отзыв, связь M:N |

При смене товара или продавца у позиции появляется другая связь, при этом
зависимая идентичность позиции остаётся `order_id × order_item_id`.
Изменение категории и перепривязка профиля отслеживаются через историю
активности связей, а не перезапись линка.

### Атрибуты, присутствие и удаления

| Модели | Что сохраняют |
|---|---|
| `sat_order`, `sat_order_status` | Оформление заказа отдельно от статуса и дат его этапов |
| `sat_customer_profile` | Индекс, город и штат профиля |
| `sat_product`, `sat_seller`, `sat_category` | Атрибуты товара, продавца и перевод категории |
| `sat_order_item` | Цену, стоимость доставки и срок отгрузки позиции |
| `sat_review` | Атрибуты отзыва |
| `sat_order_payment` | Полный набор платежей заказа; multi-active по `payment_sequential` |
| `rts_*` | Присутствие ключа в полном снимке источника на дату батча |
| `eff_*` | Изменения активности сущности или связи: исчезновение, возврат, перепривязку |
| `err_cast` | Исходное ошибочное значение, поле, ключ и контекст загрузки |

Сателлиты добавляют версию при изменении `hashdiff`, сохраняя переходы A→B→A.
Повтор одинакового состояния не создаёт новую версию атрибутов. RTS при этом
фиксирует каждое наблюдение присутствия. Физические удаления источника
становятся событиями истории; строки ODS не удаляются.

У каждой версии есть `load_dts` и `record_source`. Построение из append-only raw
даёт возможность сравнить инкрементальную загрузку с полной пересборкой.
Критичные ошибки типов и конфликтующие версии блокируют зависимые модели.

Код — [`dbt/models/ods/`](dbt/models/ods), паттерны загрузки —
[`dbt/macros/`](dbt/macros), сценарии — [приёмка ODS](.plans/ods-implementation.md).

## DDS: аналитическая модель «звезда»

DDS преобразует историю Vault в **7 измерений и 4 факта** на общей отсечке
`as_of_dts`. Восемь промежуточных моделей разрешают актуальные связи,
версии атрибутов и составы платежей. `dds.build_info` фиксирует отсечку
и идентификатор сборки; четыре представления `*__active` дают активные факты.

### Измерения

| Измерение | Зерно и назначение |
|---|---|
| `dim_product` | Версия товара: характеристики, историческая категория и её перевод |
| `dim_seller` | Версия продавца: адрес и регион |
| `dim_customer` | Постоянный покупатель: идентичность, первая покупка, число активных заказов на срезе |
| `dim_date` | Календарный день; полный календарь сохраняет периоды без заказов |
| `dim_geo` | Штат, его название и регион |
| `dim_order_status` | Статус, бизнес-группа и признак `is_revenue` |
| `dim_payment_type` | Способ оплаты и его отображаемое название |

История изменяемых атрибутов товара и продавца строится по SCD2.
Статусы, способы оплаты и штаты задаются dbt seeds. Unknown-члены и признаки
неполноты позволяют сохранить факты при отсутствии справочника.

### Факты и зерно

| Факт | Одна строка | Основное содержимое | Строк в исходном Olist |
|---|---|---|---:|
| `fct_order` | Заказ | Суммы позиций и оплат, этапы, длительности, адрес профиля на момент привязки, флаги качества | 99 441 |
| `fct_order_item` | Позиция: `order_id × order_item_id` | Цена, доставка, версии товара и продавца | 112 650 |
| `fct_payment` | Платёж: `order_id × payment_sequential` | Способ, сумма, рассрочка, активность платежа | 103 886 |
| `fct_review` | Связь отзыв × заказ | Оценка и даты отзыва | 99 224 |

Суммы в `fct_order` считаются из активных дочерних фактов и сверяются с ними.
Заказы без позиций остаются в модели с нулевыми суммами. Отдельные факты
для позиций, платежей и отзывов исключают размножение продаж при M:N-джойнах.

### Историческая привязка фактов

**HK** — постоянный ключ сущности, **SK** — ключ версии измерения.
SK вычисляется из HK и `valid_from`; интервалы SCD2 полуоткрытые:
`[valid_from, valid_to)`. Факт хранит ссылку на версию, а для ключевых сущностей —
также постоянный HK для анализа в текущих атрибутах.

`bind_dts` — первое наблюдение связи позиции с товаром/продавцом либо заказа
с профилем. На эту дату выбирается версия измерения и адрес профиля.
Поэтому смена категории товара не переносит прошлую выручку в другую категорию,
а переезд покупателя не меняет штат старого заказа. Статусы, меры и признаки
удаления фактов при этом отражают выбранный `as_of_dts`.

Дата наблюдения в DWH не равна дате покупки: источник не содержит полной
истории бизнес-изменений. Для позднего справочника задан выбор первой полной
версии того же HK на срезе. Это правило обработки неполных данных, а не
восстановление неизвестной истории источника.

Код — [`dbt/models/dds/`](dbt/models/dds); ключи, интервалы и поздние измерения —
[спецификация DDS](.plans/dds-spec.md), проверки — [приёмка DDS](.plans/dds-implementation.md).

## Принятые решения и рассмотренные варианты

### Архитектура и инструменты

| Решение | Обоснование | Рассмотренные варианты |
|---|---|---|
| Data Vault в ODS + звезда в DDS | История и интеграция источников отделены от удобной аналитической модели | Только Kimball; отчёты непосредственно из Vault; звезда как набор сложных view через PIT/bridge |
| PostgreSQL для трансформаций | Достаточен для текущего объёма, поддерживает SQL/dbt и простой локальный стенд | Greenplum / Cloudberry — при потребности в MPP; PySpark — при подтверждённой нагрузке |
| ClickHouse для BI | Отдельный сервер обслуживает аналитических потребителей готовыми данными | DuckDB как serving; BI напрямую из PostgreSQL |
| Superset как внешний клиент | Работает поверх опубликованных витрин ClickHouse | Metabase; отдельный сервис Superset внутри Compose |
| Один DAG, полный `dbt build` | Airflow управляет стадиями, dbt — графом моделей и тестами | Оператор Airflow на каждую SQL-модель; частичная сборка без учёта зависимых view |
| Пакетный ELT | Соответствует статичному источнику и воспроизводимой сборке | CDC с первого этапа, микробатчи, потоковый горячий путь, собственный OLTP-симулятор и API |

### Загрузка и история источников

| Решение | Обоснование | Рассмотренные варианты |
|---|---|---|
| GitHub Olist + SHA-256 | Версия совпадает с контрольными данными кейса | Копия Kaggle давала средний чек 159.83 вместо 159.88 |
| Инкремент с перекрытием 300 с | `_loaded_at >= watermark − lookback` учитывает поздний commit; повторы исключаются по времени источника и содержимому | Строгое `>` может терять строки; перекрытие без дедупликации удваивает загрузку |
| Append-only raw и добавление новых колонок | Сохраняются полученные версии и возможность пересборки | Upsert только текущего состояния; жёсткая схема, отклоняющая новую колонку |
| Транзакция на таблицу | Данные и снимок ключей читаются из одного снимка; запись в DWH атомарна в пределах таблицы | Общая транзакция всех таблиц — отдельное улучшение для живого источника |
| MD5 hex `char(32)` для HK | Ключи воспроизводятся при пересборке: `upper(trim(BK))`, части через `\|\|` в фиксированном порядке; нулевой ключ, только если все части пусты | Последовательности; обрезанный bigint-хеш |
| Отдельные хабы покупателя и профиля | `customer_unique_id` и `customer_id` обозначают разные сущности | Оба id в одном хабе дают 195 537 ключей вместо 96 096 покупателей; join источников до Vault теряет независимость и поздние строки |
| Загрузка Vault без соединения источников | Каждая таблица даёт собственные наблюдения; хабы пополняются из всех мест появления ключа | Сборка предварительно объединённого источника для нескольких сущностей |
| Последовательные `hashdiff` + RTS присутствия | Сохраняются переходы A→B→A; повтор одинакового состояния не создаёт версию | Последняя строка пачки через `row_number()` теряет историю при full-refresh; сателлит без схлопывания копирует raw |
| Снимки ключей и effectivity | Исчезновение ключа записывается событием, история физически не удаляется | Определение hard delete только по инкременту атрибутов |
| Multi-active для платежей | Изменение состава создаёт новую версию полного набора платежей заказа | Частичные payment-delta без контракта полного набора |
| M:N для отзывов и сателлит на хабе | Один отзыв может относиться к нескольким заказам; его атрибуты совпадают у повторов review_id | Один отзыв на заказ; атрибуты отзыва на каждой связи |
| Разделение сателлитов по источнику и изменяемости | Неизменное оформление отделено от статуса и дат этапов | Один широкий сателлит на все атрибуты |

### Аналитическая модель и качество

| Решение | Обоснование | Рассмотренные варианты |
|---|---|---|
| Техническая история по дате батча | Единая дата наблюдения и стабильный retry | Часы выполнения задачи; часы источника; дата покупки как дата изменения атрибутов |
| SCD2 из ODS, SK = хеш HK и начала версии | Уже сохранённая история определяет воспроизводимые версии измерений | Случайные SK; отдельная история через dbt snapshots |
| Один общий срез фактов | Измерения и факты согласованы на `as_of_dts` | Хранение всех снимков фактов одновременно |
| Привязка к версии на `bind_dts` | Смена категории или адреса не переписывает историческую принадлежность продажи | Всегда текущая версия измерения; версия на момент сборки отчёта |
| Явное правило позднего справочника | Известный HK получает первую полную доступную версию | Безусловная замена известной сущности на Unknown |
| Типизация до Vault, бизнес-правила в DDS | Разделены техническая интеграция и бизнес-интерпретация | Бизнес-правила в raw Vault; одинаковые правила в разных отчётах. Business vault — при нескольких независимых потребителях |
| `safe_cast`, `err_cast`, критические тесты и WARN | Ошибка сохраняет исходное значение и контекст; критическое нарушение останавливает сборку | Карантин с исключением строк; молчаливое превращение ошибок в NULL |
| Unknown и признаки неполноты | Факты без справочника и заказы без позиций сохраняются | INNER JOIN, теряющий неполные сущности; фильтрация аномальных строк |
| Четыре факта с явным зерном | Суммы заказа сверяются с позициями; платежи и отзывы не размножают продажи | Одна широкая таблица; отдельная «отгрузка продавца» при наличии дат только на уровне заказа |
| Выручка по price, чек по price + freight | Разделены стоимость товаров и расходы покупателя | Все статусы; сумма оплат вместо чека; средняя цена позиции вместо среднего заказа |
| Повторные покупки по всем статусам | Определение воспроизводит контрольные 3.12% | Только delivered даёт 3.00%; покупки в разные дни — 2.24%: это другие метрики |
| Категория по исходному коду, EN с fallback на PT | Сохраняются категории без перевода и неизвестная группа | INNER JOIN к неполному переводу |
| Полный календарь по дате оформления | Месяцы без заказов видны с нулями | GROUP BY только по фактам; месяц по дате вручения |
| Последний отзыв на заказ | В анализ доставки входит одна оценка, с детерминированным порядком выбора | Все отзывы одного заказа как независимые заказы |
| Порог штата по всем заказам, оплаты без фильтра delivered | Знаменатели соответствуют вопросам о спросе и платежах | Порог только по доставленным; учёт только оплат успешных заказов |
| Фиксированная точность и обязательные ключи зерна | Деньги хранятся в Decimal, суммы и средние имеют явный scale; пропуски ключей блокируют публикацию | Неограниченный numeric с отображением Decimal(38,19); Nullable-ключи; ноль вместо отсутствующего измерения |

### Публикация и доступ

| Решение | Обоснование | Рассмотренные варианты |
|---|---|---|
| `postgresql()` → временные таблицы → проверки → EXCHANGE | Данные переносит ClickHouse, новая версия проверяется до переключения | Live PostgreSQL engine; передача всех строк через Python; TRUNCATE опубликованных таблиц |
| Проверка всего комплекта | Сверяются схема, типы, порядок колонок, количество, зерно, суммы и инварианты | Проверка только числа строк |
| Полная смена версии таблицы | Повтор публикации даёт определённый результат без ожидания слияний | ReplacingMergeTree с ожиданием фоновой дедупликации |
| `refresh_status` последним | BI получает идентификатор и время завершённой публикации | Объявление 11 переключений общей атомарной транзакцией |
| Раздельные роли и named collection | ClickHouse читает только mart; BI имеет только SELECT; пароль DWH не передаётся в SQL-запросе | Доступ BI под владельцем DWH; секреты в тексте запроса |
| Полные разрезы в витринах | Top-10 и фильтр конкретного вопроса выбираются в SQL; знаменатели сохраняются | Хранение только top-10; доля от показанной части; среднее от средних |
| Полный build перед публикацией | Учитывает зависимости и тесты всех потребителей | `dbt run` без тестов; пересоздание таблицы без восстановления всех зависимых view |
| PIT и bridge по потребности | Дополнительные указатели и цепочки нужны при накоплении истории и дорогих соединениях | PIT/bridge и ghost-сателлиты на baseline с одной версией; виртуальная звезда на каждый BI-запрос |

## Витрины и бизнес-метрики

Выручка — стоимость товаров без доставки по доставленным заказам.
Чек включает стоимость товаров и доставки. Покупатель считается повторным,
если у него не менее двух активных заказов любого статуса за всю выгрузку.

| Анализ | Витрина | Контроль на закреплённой версии Olist |
|---|---|---|
| Продажи по месяцам | `monthly_sales` | 24 месяца; ноябрь 2016 с нулём; выручка 13 221 498.11 BRL |
| Продажи продавцов | `seller_sales` | Лидер — 226 987.93 BRL |
| Средний заказ | `order_summary` | 96 478 доставленных заказов; средний чек 159.88 BRL |

```bash

```

При агрегации учитывайте уровень показателя:

- Distinct-заказы по продавцам и категориям нельзя складывать: один заказ
  может содержать товары нескольких продавцов и категорий.
- Средние и доли пересчитываются из сумм и знаменателей; среднее от средних
  не даёт общего показателя. Для среднего чека в ClickHouse используется
  `divideDecimal(..., 10)`, сохраняющий точность до округления.
- Сроки и доля опозданий считаются по доставленным заказам с датой вручения;
  отсутствие измерения остаётся NULL.
- Доля категории считается от выручки всех категорий, даже при показе top-10.
- Итоговые summary-витрины не содержат разреза по дате или категории;
  глобальные фильтры дашборда к ним неприменимы без изменения модели.

Настройка датасетов и графиков описана в [гайде Superset](.plans/superset-guide.md).

| Защита чувствительных данных | Отдельная закрытая зона, сервисные роли, минимизация передаваемых данных | При подключении источников с персональными данными |

Масштабирование начинается с измерения I/O, памяти, времени соединений,
размера истории и конкуренции запросов. Пока PostgreSQL выполняет сборку в SLA,
сохраняется текущая архитектура. Для нагрузки, превышающей возможности одного
узла, рассматриваются Greenplum / Cloudberry и raw-лендинг S3 / Iceberg;
переход требует проверки SQL/dbt, распределения данных и стоимости эксплуатации.
Поток событий можно обслуживать Kafka и ClickHouse; Spark/Flink нужны при
вычислениях с состоянием. Конкретный переход определяется нагрузочным тестом.

## Загрузка и оркестрация

Источник содержит заказы, позиции, покупателей, продавцов, товары, платежи,
отзывы и перевод категорий. Версия Olist закреплена на коммите
`d9e49802f3e92d09ee94ab9ccc5e457f207a8959`; файлы проверяются по
[манифесту SHA-256](scripts/olist.sha256). `make seed` загружает источник,
затем DAG `marketplace_elt` выполняет следующие этапы.

| Этап | Назначение |
|---|---|
| `open_batch` | Фиксирует единые `batch_id` и дату загрузки в UTC; отклоняет дату, нарушающую порядок истории |
| `extract_load` | Читает источник без изменения значений; добавляет наблюдения в raw, сохраняет полные снимки ключей и подхватывает новые колонки |
| `dbt_build` | Выполняет полный граф SQL-моделей со справочниками и тестами: типизация → история → аналитическая модель → агрегаты |
| `publish_clickhouse` | Загружает временные таблицы, проверяет весь комплект, переключает витрины и последним обновляет статус публикации |

DAG запускается ежедневно или вручную; одновременно выполняется один запуск.
Ошибка EL или dbt блокирует публикацию. Ошибка загрузки или проверки временных
таблиц сохраняет опубликованные данные. Повтор запуска без изменений источника
не удваивает показатели витрин.

Дата батча — `logical_date`, а при её отсутствии у ручного запуска —
фиксированный `run_after`. Повтор задачи сохраняет дату. Более ранние батчи
и коллизии дат отклоняются до загрузки: инкрементальная история требует
монотонного `load_dts`. Подробнее — [даты батчей](airflow/README.md).

## Проверки и ограничения

```bash
make dbt ARGS="build"
docker compose exec -T airflow python /opt/project/scripts/check_batch_time.py
docker compose exec -T airflow python - < scripts/check_ods.py
docker compose exec -T airflow python - < scripts/check_dds.py
```

Тесты проверяют зерно, ключи, интервалы истории, сверку исходных строк,
сумм и контрольных ответов. Сценарии ODS/DDS дополнительно проверяют изменения,
удаление и возврат сущности, поздние справочники и равенство инкремента
с полной пересборкой. Они используют временные БД и требуют CREATE DATABASE.

В [отчёте приёмки ClickHouse](.plans/clickhouse-publish-implementation.md)
зафиксированы 95 877 строк в 11 витринах, повторные прогоны без удвоения,
проверка прав BI и сохранность данных при отказах до переключения.
Полная сборка модели: 488 PASS, 3 WARN, 0 ERROR; предупреждения отражают
аномалии дат исходных заказов.

Границы текущей реализации:

- **История отражает наблюдения DWH.** Исправление источника неотличимо
  от реального изменения без business-effective timestamp; историческая
  загрузка требует соответствующих снимков и пересборки.
- **У EL есть контракт метаданных.** Staging требует `_batch_id`, `_extracted_at`
  и снимки ключей; произвольную исходную raw-базу сначала нужно пропустить через EL.
- **Пустые снимки и наборы требуют явного события.** Без журнала батчей нельзя
  обнаружить исчезновение последнего ключа или полного набора платежей;
  произвольные частичные изменения платежей не поддерживаются.
- **Удаление отдельной связи отзыв–заказ покрыто не полностью.** Для него
  нужен собственный снимок пар и история активности.
- **Публикация комплекта не атомарна.** Сбой во время 11 EXCHANGE может оставить
  смешанный комплект. Транзакции EL независимы по таблицам; общего снимка
  между PostgreSQL и ClickHouse нет.
- **Контроли привязаны к датасету.** Месячная витрина имеет окно
  `[2016-09-01, 2018-09-01)`; все 11 витрин должны быть непустыми.
  Для нового периода эти условия нужно пересмотреть.

## Быстрый запуск

Нужны Docker Engine, Docker Compose v2 с поддержкой `additional_contexts`, Make,
Bash, curl и `sha256sum` либо `shasum`. Первый запуск требует доступа к образам,
Python-пакетам и CSV. Из корня проекта:

```bash
make env
make up
make ps
```

Дождитесь готовности Airflow, затем загрузите источник и запустите пайплайн:

```bash
make seed
make run
```

`make env` создаёт `.env` со случайными паролями, `make up` запускает сервисы
и инициализирует DWH. `make run` ставит запуск в очередь; результат проверяется
в Airflow: все задачи `marketplace_elt` должны завершиться со статусом `success`.

| Сервис | Адрес с хоста | Подключение |
|---|---|---|
| Airflow | `http://127.0.0.1:18090` | Локальный стенд без отдельного входа |
| PostgreSQL source | `127.0.0.1:15432` | БД `marketplace`, пользователь/пароль `hack` |
| PostgreSQL DWH | `127.0.0.1:15433` | БД `dwh`, пользователь `dwh`, пароль `DWH_PASSWORD` из `.env` |
| ClickHouse | HTTP `127.0.0.1:18123`, native `127.0.0.1:19000` | БД `mart`; BI-пользователь `bi_reader`, пароль `CLICKHOUSE_BI_PASSWORD` из `.env` |

В контейнерной сети адреса — `source:5432`, `dwh:5432`, `clickhouse:8123`.
Для Superset используйте адрес ClickHouse, доступный из сети его установки.
Пользователь `bi_reader` имеет только SELECT на `mart.*`.

| Команда | Назначение |
|---|---|
| `make logs S=airflow` | Логи оркестратора |
| `make psql-source` / `make psql-dwh` | SQL-консоль источника / хранилища |
| `make psql-analyst` | Проверка доступа под ролью аналитика |
| `make ch` | SQL-консоль ClickHouse |
| `make dbt ARGS="build"` | Полная сборка модели с тестами |
| `make down` | Остановка с сохранением данных |
| `make nuke` | Удаление контейнеров и томов с данными |

Для диагностики доступны `make el` и `make publish`: они вызывают те же стадии,
что и DAG. Ручные загрузки, сборки и публикации выполняются последовательно,
без одновременного запуска DAG. После `make nuke` повторите полный запуск
от `make env` до `make run`. Имя Compose-проекта `mp-dwh` определяет имена томов.
