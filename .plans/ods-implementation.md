# Приемка staging / ODS — 28.10.2026

Все преобразования выполняет dbt: 8 staging views, 5 views снимков ключей,
7 хабов, 5 линков, 8 обычных сателлитов, 1 multi-active сателлит,
5 RTS, 5 entity effectivity + 1 relationship effectivity и пересчитываемая таблица `ods.err_cast`.
Модели находятся в `dbt/models/{staging,ods}`, собственные паттерны — в
`dbt/macros`, проверки — в `dbt/tests` и `dbt/models/ods/_ods.yml`.
DDS, mart, ML, EL и raw не изменялись.

## Принятые контракты

- HK: `md5` hex `char(32)`, `upper(trim(BK))`, составные части через `||`;
  нулевой HK только когда **все** части пустые. Хеш позиции:
  `(order_id, product_id, seller_id, order_item_id)` в этом порядке.
  Идентичность позиции хешируется по исходному текстовому dependent BK;
  отдельно `order_item_id` безопасно типизируется в integer.
- `load_dts = raw._extracted_at`, `record_source = raw._source_file`,
  `batch_id = raw._batch_id`. В снимках `_source_file` отсутствует, поэтому
  `record_source = '<таблица>__keys'`.
- Все raw-строки остаются в staging. Хабы пополняются UNION ALL из всех
  источников, где встречается соответствующий BK; линки не соединяют источники.
  `customer_unique_id` и `customer_id` раздельны. `hub_category` содержит
  системный нулевой член; ghost-сателлиты без PIT не создаются.
- Снимок item содержит только `(order_id, order_item_id)`. Staging разрешает
  его в **последнюю версию того же источника** с `load_dts <= snapshot.load_dts`
  set-based join по driving BK; при смене product/seller прежний link получает
  удаление, новый — присутствие. Снимок без соответствующей наблюдавшейся
  строки блокируется `not_null`; конфликт идентичности в один момент блокируется
  staging-тестом, а не выбирается случайным порядком `lag`.
- Обычные сателлиты схлопывают только последовательные одинаковые hashdiff,
  поэтому A→B→A сохраняет три версии. RTS сохраняет каждое присутствие.
  Все incremental модели используют append, без update/delete.
- `eff_product_category` хранит историю single-valued связи с driving `product_hk`.
  Смена A→B деактивирует прежний link и активирует новый; возврат B→A
  создает новые события, поэтому история не теряется за insert-only link.
  Удаление самого продукта задает `eff_product`; DDS учитывает оба флага.
- `sat_order_payment` считает hashdiff по всему упорядоченному набору
  `payment_sequential` родителя. Изменение/исчезновение одной строки при
  наличии оставшихся строк приводит к вставке **полного нового набора**.
  Full-refresh и последовательные прогоны используют одну и ту же логику
  переходов наборов. Уникальность версии здесь — `(order_hk, load_dts,
  payment_sequential)`, у обычного satellite — `(HK, load_dts)`.
- `safe_cast` проверяет `pg_input_is_valid` с полным типом, включая typmod;
  сначала выбирается валидный текст/NULL внутри CASE, затем выполняется cast
  снаружи. Это защищает также от constant folding ошибочного литерала.
- `err_cast` сохраняет исходное значение, таблицу/колонку, полный BK строки,
  batch и load_dts; критичные колонки/пустые обязательные ключи — error,
  остальные неприводимые значения — warn. Необычный формат текстового BK
  и только формат — warn. Неизвестный статус — error staging-теста.

## Ограничения upstream, которые нельзя восстановить из текущего raw

1. **Оплаты требуют полного набора родителя на каждый наблюдаемый load_dts.**
   Текущий EL передает инкрементальные строки, не снимок payment keys/наборов.
   Поэтому частичное обновление одного платежа неотличимо от полного набора,
   в котором остальные платежи исчезли; полностью исчезнувший набор вообще
   не оставляет события. Полная перезаливка источника и полные parent-наборы
   поддерживаются; произвольный CDC/partial delta — нет. Для production
   нужны полные parent sets и явный empty-set marker либо payment key snapshots
   с batch ledger. Модель не обещает обнаруживать недоступные upstream события.
2. **Полностью пустой снимок ключей не оставляет строки** в `raw.*__keys`.
   RTS/eff видит непустые снимки; удаление последнего ключа без batch ledger
   обнаружить невозможно. Нужен отдельный журнал успешных полных снимков.
3. `sat`/`rts`/`eff_sat` предполагают монотонные `_extracted_at` и неизменность
   уже обработанных батчей. Backfill с более ранним load_dts, исправление hard
   rules или reinterpretation старого raw требуют `dbt build --full-refresh`.
   Текущий incremental watermark не добавляет автоматическую новую версию
   при изменении SQL-приведения старых строк. Для этого нужен отдельный
   контракт reprocessing/correction load_dts.
4. Две разные версии обычного satellite или два разных link HK одного
   dependent BK в одном load_dts — **ошибка входного контракта**. Staging tests
   блокируют соответствующих потребителей при `dbt build`; `dbt run` без tests
   не является приемкой. В `payment_sequential` допускается несколько строк
   родителя, но конфликтующие атрибуты одного sequential в одном батче — error.
5. На следующем этапе DDS/mart должны явно зависеть от gate
   `err_cast_critical` (либо запускаться отдельной задачей только после успешного
   ODS build). Нельзя полагаться, что независимая ветка dbt автоматически
   остановится из-за теста таблицы `err_cast`, от которой она не зависит.

## Проверки

- Первый полный baseline: `dbt build --profiles-dir .` — **234/234 PASS**,
  31 incremental + 1 table + 13 views + 189 tests, 0 WARN/ERROR, ~30 s.
  Предыдущий эксперимент с lateral item lookup отменен; заменен set-based join.
- Проверены контрольные размеры: order 99 441; customer 96 096;
  profile 99 441; product 32 951; seller 3 095; review 98 410;
  category 74 с нулевым членом; item link 112 650; order-review link 99 224;
  payments 103 886; `err_cast` 0. `sat_category` 71: два PT-названия без
  перевода и нулевой член не создают вымышленных атрибутов перевода.
- RTS содержит два имеющихся непустых снимка: например orders 198 882,
  items 225 300. Сверки сравнивают raw-историю с staging без фильтрации,
  хабы/линки — на distinct HK, RTS — на `(HK,load_dts)`, satellite — на
  переходах hashdiff, multi-active — на сумме размеров изменившихся наборов.
- Отдельные staging tests проверяют конфликты версий до downstream модели;
  generic tests — уникальность, not_null и ссылочную целостность.
- Дополнительные `hash_contract` и `reconcile_payment_history` проверяют
  нормализацию, нулевой составной HK, null в hashdiff, invalid literal,
  numeric overflow и число полных payment-наборов в истории.
- Финальный live `dbt build --profiles-dir .` после добавления relationship
  effectivity и проверок типов: **249/249 PASS**, 32 incremental + 1 table +
  13 views + 203 tests, 0 WARN/ERROR, 29 s. `dbt parse --profiles-dir .` успешен.
- Повторный build не изменил ни одной строки в ранее построенных 32 ODS
  таблицах: сравнение count и `md5(string_agg(md5(row::text), '' order by
  md5(row::text)))` до/после — полное равенство всех 32 подписей.
  У новой `eff_product_category` на baseline 32 951 активная связь; ее
  уникальность и полная история проходят отдельные dbt tests.
- Независимая приемка родительским агентом: **8 этапов прошли** в отдельной
  временной БД. Первичная, повторная, две инкрементальные сборки и
  `--full-refresh` — **249/249 PASS** на каждом этапе. Проверены разные
  customer profiles одного покупателя, M:N отзывов, новая версия статуса,
  схлопывание одинаковых атрибутов, смена товара у позиции, исчезновение
  платежа из полного parent-набора, удаление/возврат продавца и категория
  A→B→A (включая возврат к unknown).
- После трех fixture-батчей **все 33 ODS-таблицы** совпали между incremental
  и full-refresh по числу строк и подписи отсортированного полного содержимого.
  Повтор без новых данных не изменил ни одной подписи.
- Негативные сценарии сработали ожидаемо: неприводимый вес товара создал
  `err_cast` с `warn` (сборка успешна); неприводимая цена позиции вызвала
  `err_cast_critical` с `fail` (сборка с ненулевым exit code); две категории
  товара на один load_dts вызвали `stg_product_category_conflicts` с `fail`.
  Исходное ошибочное значение и контекст остались в журнале.
- Воспроизводимый harness: `scripts/check_ods.py`. Запуск из корня проекта:
  `docker compose exec -T airflow python - < scripts/check_ods.py`.
  Python только создает fixtures, запускает dbt и проверяет результаты;
  **все модели и трансформации остаются в dbt**. Требуются локальные права
  CREATE DATABASE. Harness копирует только DDL raw во временную БД,
  удаляет ее в `finally`; рабочие source/raw/ODS не изменяет. Логи и
  подписи сохраняются в `/tmp/ods-review-*` внутри Airflow.
