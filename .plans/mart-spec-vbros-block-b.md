## Общее

- Все витрины читают активные факты (`*__active`). Выручка и «доставлено» —
  через `dim_order_status.is_revenue`, статус не захардкожен.
- Средние и доли хранятся как числитель и знаменатель или как точное значение;
  округление — только при показе. Доли — 0–1.
- Витрины хранят полный разрез (все товары / штаты / годы); выбор под конкретный
  вопрос («товар-лидер», «≥ 500 заказов», «2018») — в SQL ответа. (по умолчанию)
- «Доставлено с датой» = `is_revenue` и `order_delivered_customer_ts is not null`.
  Срок доставки — `fct_order.to_customer_days`, опоздание — `fct_order.is_late` (§18 DDS).

## 1. Правки витрин блока А под §20

### 1.1. `seller_sales`

Группировка по постоянному продавцу (`fct_order_item.seller_hk`), а не по
атрибутам версии. `seller_city` и `seller_state` — из **текущей** версии
`dim_seller` (`is_current`) этого `seller_hk`. Переехавший продавец — одна строка
с текущим адресом. Unknown-продавец — отдельная группа `__unknown__`, как сейчас.

### 1.2. `category_sales`

Выручка по категории — по версии товара на момент продажи (`product_sk`, §20):
прошлые продажи остаются в прежней категории. Группировка — только по
`category_code`. Названия (`category_name_original`, `category_name_english`,
`category_label`, `is_translation_missing`) — из текущего состояния категории:
по текущим версиям `dim_product` с этим `category_code`; если текущих товаров
с этим кодом нет — из последней по `valid_from` версии с этим кодом. (по умолчанию)
Одна категория — одна строка, даже если перевод пришёл позже части продаж.

### 1.3. Документация

В `mart-implementation.md` фраза «атрибуты по SK факта — версия, текущая на срезе»
заменяется описанием §20 и правил 1.1–1.2.

## 2. Блок Б

### 2.1. `product_price_history` — вопрос 6

- Зерно: товар (`product_hk`) × дата покупки × цена. Только доставленные заказы.
- Колонки: `product_id`, `sale_date`, `price`, `unit_count` (= число позиций),
  `orders_count`; на уровне товара — `distinct_price_count`, `product_unit_count`.
- Товар-лидер: максимум `distinct_price_count`, затем `product_unit_count`, затем
  `product_id`. На текущих данных — `437c05a395e9e47f9762e677a7068ce7`, 31 цена, 151 единица.
- Ответ: дата, цена, продано единиц — по лидеру, сортировка по дате и цене.
- Товар идентифицируется постоянным ключом, смена категории не дробит историю цены.

### 2.2. `delivery_by_state` — вопрос 7

- Зерно: штат покупателя (`upper(trim(fct_order.customer_state))`, на момент заказа по §20).
  Пустой штат — `__unknown__`. Название и регион — из `dim_geo`.
- `orders_count` — все активные заказы штата, любой статус (база порога 500).
- `delivered_measured_count` — доставленные с датой; `delivery_days_sum`,
  `avg_delivery_days`, `late_count`, `late_share` — по ним.
- Ответ: штаты с `orders_count >= 500`. На текущих данных — 17 штатов.

### 2.3. `order_status_funnel` — вопрос 8

- Зерно: статус заказа; все члены `dim_order_status`, включая статусы с нулём
  заказов и `__unknown__`. (по умолчанию)
- Колонки: `order_status`, `status_group`, `orders_count`, `order_share`
  (от всех активных заказов), `orders_without_items_count` (`items_count = 0`).
- Контроль: сумма `orders_count` = 99 441, без позиций — 775.

### 2.4. `payments_by_state_year` и `payments_by_type` — вопрос 9

- Платёж — строка активного `fct_payment`. Статус заказа не фильтруется:
  считаются все платежи. (по умолчанию)
- `payments_by_state_year`: зерно — штат покупателя заказа (как в 2.2) × год даты
  покупки заказа. Колонки: `payments_count`, `payment_amount`, `installments_sum`,
  `avg_installments`.
- `payments_by_type`: зерно — способ оплаты за весь период. Те же колонки.
- `not_defined` — обычная строка; рассрочка 0 учитывается как есть, отдельной
  колонкой `zero_installments_count`.
- Ответ: штаты за 2018 год + все способы оплаты.

### 2.5. `review_delivery` — вопрос 10

- Оценка заказа — **последний** активный отзыв заказа: максимум
  `review_creation_ts`, затем `review_answer_ts`, затем `review_id`.
  Один заказ — одна оценка.
- Зерно: оценка 1–5 (плюс строка `NULL`, если у отзыва нет оценки).
- `orders_count` — заказы с этой оценкой, любой статус;
  `delivered_measured_count`, `avg_delivery_days`, `late_count`, `late_share` —
  по доставленным с датой.
- Контроль: сумма `orders_count` = числу активных заказов, у которых есть отзыв.

## 3. Проверки

- Тесты dbt: уникальность зерна каждой витрины; сумма `orders_count` в
  `order_status_funnel` = числу активных заказов; сумма `payment_amount` в обоих
  разрезах = сумме активных платежей (по штатам — по всем годам);
  `review_delivery` — сверка с числом заказов с отзывом; доли в 0–1.
- Регрессия блока А не меняется: контрольные тесты `mart_control_*` проходят.
- Сценарий вброса в harness (`scripts/check_dds.py` собирает и `mart`):
  - категория A → B: выручка A от продаж до смены не изменилась, новая продажа — в B;
    в `category_sales` нет дублей кода;
  - переезд продавца: в `seller_sales` одна строка с новым городом;
  - переезд покупателя: старый заказ остаётся в старом штате в `delivery_by_state`.
- SQL ответов `analysis/business_questions/sql/06_*.sql`–`10_*.sql` и README.
