# Приёмка DDS — 28.10.2026

## Что реализовано

Контракт `.plans/dds-spec.md` реализован в dbt: 3 seeds, 8 промежуточных
таблиц, 7 измерений, 4 базовых факта, 4 views активных строк и `build_info`.
Все 20 табличных моделей полностью пересобираются в схеме `dds`; seeds
также находятся в `dds`. Новые макросы: `dds_sk`, `dds_latest`, `dds_scd`.
Трансформации — set-based SQL PostgreSQL, без lateral lookup.

В ODS добавлены `eff_order_profile` и `eff_customer_profile` на существующем
`relationship_effectivity`. Каждая модель описана и проверяется в `_ods.yml`;
для обеих связей есть staging-тест конфликтов и двусторонняя сверка полной
истории с исходными наблюдениями. Прежние ODS SQL-модели не менялись.

`_dds.yml` задаёт PK, not_null, уникальность составного зерна и FK.
`dbt/tests/dds_*` проверяют интервалы и Unknown, активные связи,
сверку зерна фактов с ODS и сумм дочерних фактов, предупреждения по
аномалиям, неполным сущностям и неизвестным кодам справочников.

`scripts/check_dds.py` создаёт отдельную временную БД, копирует только
DDL raw, загружает fixtures несколькими батчами, запускает dbt и проверяет
результат. БД удаляется в `finally`. Python не преобразует данные DDS.
Docstring DAG `marketplace_elt` теперь включает DDS и seeds в `dbt_build`.
Mart, ClickHouse, Superset, EL и raw DDL не менялись. Исходные пользовательские
изменения и неотслеживаемые файлы сохранены; коммитов и push нет.

## Принятые контракты

- Отсечка `as_of_dts` общая для всех моделей: явная dbt var либо максимум
  `load_dts` всех 34 инкрементальных ODS-моделей. Все состояния ограничены
  отсечкой; `build_info` хранит её, время сборки и dbt invocation.
- `dds_sk` в точности использует md5 HK и начала версии с UTC-форматированием
  микросекунд. Системный Unknown имеет нулевые HK/SK. Известные товары и
  продавцы без satellite получают собственную неполную версию с появления
  хаба; поступившие атрибуты создают новую версию.
- Для `dim_product` и `dim_seller` объединяются точки наблюдений; состояние
  каждого источника выбирается на точку, одинаковые последовательные
  наборы атрибутов схлопываются. Удаление и неполнота участвуют в сравнении.
  Интервалы полуоткрытые, текущая версия открыта до `infinity`.
- У `dim_customer` одна версия с начала хаба; число активных заказов и
  когорта пересчитываются на срезе через обе действующие связи профиля.
- Статические seed-измерения имеют начало обычных версий
  `1970-01-01 00:00:00+00`; начало Unknown — `-infinity`. HK обычных seed-членов
  использует тот же `md5(upper(trim(code)))`, что ODS; SK — общий `dds_sk`.
- География заказа сохраняет значения ODS. Для сопоставления штатов используется
  `upper(trim(state))`; города дополнительно не нормализуются. При отсутствии
  профиля география NULL; при отсутствии покупателя сохраняется география
  профиля, а customer SK направляется в Unknown.
- Товар содержит категорию PT/EN и историю поздних переводов. Пустая категория
  получает `__unknown__`, известная без перевода сохраняет PT и NULL EN.
- Факты ссылаются на текущие версии измерений выбранного среза. Выбор item
  выполняется по приоритету active / без eff / последнее удаление с заданными
  контрактом критериями ничьей. Старые связи не размножают зерно.
- Исчезнувший платёж остаётся с последними известными атрибутами; активность
  определяется последним полным parent-набором. Удаление родителя не
  каскадируется на дочерние факты; удаление продавца не удаляет продажи.
- Суммы и количества заказа учитывают только активные дочерние строки;
  отсутствие строк даёт нули. Все три длительности считаются от покупки
  в дробных днях; отрицательная длительность заменяется NULL. Просрочка —
  разность календарных дат. Отрицательное время ответа отзыва — NULL.
- Календарь охватывает полные годы всех дат заказа на срезе. Неизвестная дата
  получает `-1`, в том числе дата отзыва вне этого диапазона.
- У каждой DDS-модели есть явная зависимость от `err_cast`. При `dbt build`
  критический gate и ошибки upstream-тестов пропускают DDS. Seeds могут
  обновляться отдельно; гарантии gate относятся к моделям DDS.

## Ограничения

Наследуются ограничения ODS: нет маркера пустого платёжного набора и пустого
снимка ключей; нужны полные parent-наборы платежей и монотонные неизменяемые
батчи. Исчезновение одной связи отзыв–заказ при живом отзыве необнаружимо.
Бизнес-время изменения атрибутов неизвестно; история использует `load_dts`.
Публикация атомарна по таблице, а не по всей схеме; `dbt run` без тестов не
обеспечивает gate. Справочники seed не имеют самостоятельной истории изменений.

Живой DAG выполнен отдельно после приёмки Codex (раздел ниже).

## Вопросы к владельцу

1. **Детерминизм `build_info`.** Требование равных полных подписей всех таблиц
   несовместимо с меняющимися `built_at` и `dbt_invocation_id`. Минимальное
   решение: сравнивать полные подписи остальных таблиц и только `as_of_dts`
   у `build_info`. При проверке gate сравнивается полная строка `build_info`.
2. **Начало статических справочников.** В спецификации оно не определено.
   `to_char('-infinity'::timestamptz, ...)` возвращает NULL в PostgreSQL,
   поэтому для обычных seed-членов выбрана фиксированная дата Unix epoch.
   Формула SK и контракт Unknown сохранены.
3. **Штаты и Unknown.** §14 требует сохранить географию как в ODS, а §17
   требует заменять неизвестные коды в факте на `__unknown__`. Для штатов
   приоритет отдан явному контракту §14: исходный штат сохраняется, неизвестный
   код даёт warn; `dim_geo` содержит Unknown для разрешения такой ссылки
   потребителем. Дополнительный geo SK, которого нет в колонках контракта,
   не добавлялся. На текущих данных неизвестных кодов нет.
4. **База длительностей.** Для `to_carrier_days` и `to_customer_days` не названа
   начальная дата. Выбрана дата покупки, как для `approve_days`; отрицательные
   интервалы — NULL. Для `answer_hours` также выбрана NULL при отрицательном
   интервале, без потери строки отзыва.

### Вопросы к владельцу

1. **HK при отсутствии версии на bind_dts.** §20 явно требует Unknown SK,
   если версии на момент привязки нет. Одновременно требование постоянного
   известного HK и error-тест одинакового HK у факта и версии несовместимы
   в этом случае. Пример: заказ с профилем появился в батче 1, постоянный
   покупатель этого профиля впервые появился в батче 2. Консервативно
   сохранена согласованная пара **Unknown SK / Unknown HK**; связь и известный
   HK покупателя остаются в `int_order_profile_on_slice` и ODS, география
   выбирается независимо по §20. Этот крайний случай включён в harness.
   Если нужен известный HK даже при Unknown SK, потребуется явное исключение
   из требования одинакового HK; такого исключения реализация не вводит.


### Уточнение позднего измерения для блока Б (28.10)

Уточнённый §20 закрывает вопрос 1 выше: отсутствие версии на bind_dts
теперь использует первую полную версию HK на срезе, иначе первую версию HK.
Unknown остаётся только для неизвестного HK или HK, отсутствующего в измерении.
Это заменяет прежние формулировки про Unknown при отсутствии версии на bind_dts
в этом разделе и пункте 8 приёмки выше.

и `fct_order`, а также ожидание O5 в harness. Макрос расширяет первый непрерывный
SCD-интервал до -infinity для соединения, сохраняя исходные valid_from/valid_to
измерения и выбирая первую полную версию вместо неполной. Полные исторические
версии не меняются. O5 до прихода покупателя остаётся Unknown; после прихода
получает известный HK/SK первой полной версии, география остаётся Late.
