## 1. Кейс и что сдаём

**Кейс «Модель маркетплейса: от корзины до выкупа».** Capibara — маркетплейс из Сан-Паулу, данные — открытый датасет **Olist** (09.2016–10.2018, обезличен, ~550 тыс. строк в 8 файлах). Подсистемы (заказы, платежи, отзывы) писались в разное время и хранят данные по-своему; в выгрузке есть пропуски, несостыковки и неочевидные места. Мы — архитекторы данных: нужна модель, на которую смогут опереться аналитики.

Материалы: [репозиторий кейса](https://github.com/daniilivanovp-droid/hackathon-students) (`docs/handout.md`, `docs/tasks.md`).

**Правила кейса**
- `raw` — то, что приехало от источников, менять нельзя; все колонки `text`.
- Ответы на вопросы считаются **из нашей модели**, не из `raw`.
- Решения придётся объяснить: на защите спрашивают про наш код («почему такой ключ», «что будет с отчётом, если поменяются данные», «как убедились, что ничего не потеряли»).

**Что сдаём**
1. Код, который собирает модель из `raw` с нуля на чистой базе (у нас — репозиторий со стендом, §13).
2. Ответы на 10 вопросов: 5 в начале (`tasks.md`, блок А), 5 в середине хакатона **вместе со вбросом — изменением модели**, которое тоже надо реализовать (§11).
3. Записка о решениях — не больше половины страницы A4: что выбрали, от чего отказались, почему.
4. Концепция дашборда: область выбираем сами; для каждого показателя — формула, уровень расчёта, источник; отдельно — какие показатели нельзя складывать по срезам. Эксперт на брифинге: под концепцию стоит **реализовать витрину**.
5. Стратегия развития (§15).

## 2. Команда

Бэкенда и фронтенда в команде нет. **Итоговый продукт — стенд** (§3, §13): source → Airflow → DWH (dbt) → витрины → ClickHouse → Superset.

| Зона | Артефакты |
|---|---|
| **Data Engineer** | стенд, EL, dbt (`ods` / `dds` / `mart`), тесты, Airflow, ClickHouse |
| **Аналитик** | ответы на вопросы, концепция дашборда и витрина под неё, сторителлинг |
| **ML** | модель срока доставки (§10), скоринг в DAG |

## 3. Архитектура

```
 CSV Olist ──seed──► source (Postgres, raw как у организаторов)
                          │
                          │ Airflow: инкрементальный EL по _loaded_at
                          ▼
   DWH (Postgres) ── raw (append-only, _batch_id) ─dbt─► ods (Data Vault) ─dbt─► dds (звезда, SCD2) ─dbt─► mart
                                                                                                         │
                                       ml.predictions_* ◄── батч-скоринг (Airflow) ◄── фичи из dds/mart ─┤
                                                                                                         ├─► ClickHouse mart.* ─► Superset
                                                                                                         └─► reverse ETL       (если есть время)
```

**Принципы**
- **ELT:** данные приезжают в DWH как есть, все трансформации — внутри Postgres через dbt.
- **dbt — основа качества:** тесты = самопроверки, `dbt build` = воспроизводимая сборка, макросы = единообразие, `dbt docs` (lineage) = прозрачность.
- **Airflow — оркестратор всей цепочки:** EL → dbt build → (ML) → ClickHouse → (reverse ETL). Модели при этом переносимы: `raw` копируется один в один со структурой организаторов, поэтому dbt собирается и на их базе, если указать другой хост.
- **Data Vault в `ods`** — реакция на новые источники и изменения формата без переделки существующего: новый источник или формат → новый сателлит / хаб / линк.
- **Звезда в `dds`** — удобный слой для витрин и аналитиков; все бизнес-правила (unknown, нормализация, группы статусов) живут здесь, в одном месте.

**Убрано из v1:** OLTP-бэкенд и его схема, replay, горячий путь (микробатч `*/2`, `hot.*`, словари), Cloudberry (→ стратегия), PII-слой (→ стратегия), карантин строк (→ флаги и журнал ошибок приведения `ods.err_cast`, §9), API кабинета продавца.

## 4. Источник и EL

### 4.1 Source
- Postgres с init-скриптами организаторов (`source/init/` — копия `scripts/init` из репозитория кейса): схемы `raw` / `core` / `mart`, 8 таблиц `raw.*`, все колонки `text` + `_source_file`, `_loaded_at`. Пустую схему `core` в `source` создаёт init организаторов, мы её не используем; в DWH слоя `core` нет — модель живёт в `ods` + `dds` (согласовано с проверяющим).
- **Воспроизводимость:** `make seed` = `scripts/download_data.sh` (CSV с GitHub Olist в `data/`, как у организаторов) + `scripts/load_raw.py` (TRUNCATE + COPY в одной транзакции, сверка числа строк с CSV). Результат совпадает с их `load_raw.py` байт в байт (проверено 28.10).
- **Данные — только с GitHub Olist, не с Kaggle.** Версии различаются: на GitHub zip-индексы без ведущего нуля (`9790` вместо `09790`), у 67 позиций `freight_value` = `price`, у 3 оплат `payment_installments` 10 вместо 1. Организаторы качают с GitHub. Версия закреплена: коммит `olist/work-at-olist-data@d9e4980` + sha256 в `scripts/olist.sha256`. `make data` перекачивает любой несовпавший файл, `load_raw.py` не грузит файл с другим хешем (обхода нет).

### 4.2 EL source → DWH `raw` (Airflow)
- **Инкремент по водяному знаку с перекрытием.** В источнике нет `updated_at` и первичных ключей, поэтому водяной знак — `_loaded_at`: забираем строки с `_loaded_at >= max(_src_loaded_at) − lookback`. Не строгое `>`: `now()` — время начала транзакции, транзакция, закоммиченная после нашего чтения, принесла бы строки ниже водяного знака, и они потерялись бы. **Повторы перекрытия EL не вставляет:** у источника организаторов все строки одной заливки имеют один `_loaded_at`, и при `>=` каждый прогон заново выбирал бы всю таблицу. Строка вставляется, только если в окне перекрытия `raw` нет строки с тем же `_src_loaded_at` и тем же содержимым (md5, NULL ≠ `''`). Перезаливка источника (новый `_loaded_at`) вставляется целиком, её схлопывает макрос `sat` (§6). ТЗ: `.plans/el-tz.md`.
- `raw` в DWH — **append-only**. Служебные колонки: `_src_loaded_at` (это `_loaded_at` источника, переименован — своё имя занято бы дважды), `_batch_id` (`run_id` Airflow), `_extracted_at`; под CDC заранее nullable `_op`, `_lsn`, `_commit_ts` — при переходе `raw` остаётся той же таблицей. Дедупликация и история — в `ods` через hashdiff сателлитов.
- **Снимок ключей.** На каждом прогоне EL дополнительно выгружает **все** бизнес-ключи таблицы в `raw.<таблица>__keys` (ключ, `_batch_id`, `_extracted_at`). Инкремент приносит только изменившиеся строки, по нему исчезновение строки не видно; снимок ключей кормит record tracking и effectivity-сателлиты (§6). Первые таблицы: `orders`, `order_items`, `products`, `sellers`, `order_reviews`. Оплаты не нужны: пропажу платежа ловит multi-active сателлит.
- **Подводный камень:** `load_raw.py` организаторов делает `TRUNCATE` + `COPY`, при перезаливке у всех строк новый `_loaded_at` → инкремент заберёт таблицу целиком. Это не ломает модель: в сателлитах вставятся только изменившиеся версии (hashdiff). Проговариваем на защите.
- **Schema drift:** новые колонки источника автоматически добавляются в DWH `raw` (`pipelines/source_to_raw.py`). Это прямая подготовка ко вбросу «изменился формат».
- EL для 8 таблиц Olist реализован в `pipelines/source_to_raw.py`; старый `pipelines/oltp_to_raw.py` удалён. Сценарии приёмки — `.plans/el-tz.md`.

## 6. ODS — Data Vault 2.0 (raw vault)

Методология — **Data Vault 2.0, классический, без отклонений**, в объёме raw vault: хеш-ключи вместо последовательностей, `hashdiff`, insert-only, multi-active сателлиты, ghost-записи, same-as link (когда у одной сущности появятся дубли ключей). Разделение правил по DV 2.0: **жёсткие** (приведение типов, тримминг ключей) — до vault, **мягкие** (бизнес-правила: unknown, группы статусов, нормализация городов) — после, в `dds`. **PIT, bridge и business vault сейчас не строим**, их развитие — §15. PIT не имеет смысла на текущих данных: одна загрузка, у каждого ключа ровно одна версия в каждом сателлите (проверено на `source`: дублей ключей 0, одна дата `_loaded_at`) — все указатели PIT совпали бы, и он был бы равен простому джойну.

**Архитектура слоёв: vault + материализованная звезда поверх.** Это и есть каноничная схема DV 2.0: information mart поверх vault — звезда. Она материализуется моделями dbt, а не собирается view из PIT + bridge на каждый запрос: BI читает готовые таблицы, тесты dbt идут на фактах, зерно факта видно в коде. Bridge сейчас не нужен: зерно `fct_order_item` совпадает с `link_order_item`, до категории — один джойн (развитие — §15).

**Конвенции**
- Хеш-ключ хаба — от бизнес-ключа; хеш-ключ линка — от бизнес-ключей участников; в сателлите — `hashdiff` от атрибутов. По DV 2.0 — полный хеш (а не bigint-обрезка из v1).
- **Хеш — md5 → `char(32)`** (hex; совпадает с `md5()` в PG и `lower(hex(MD5()))` в ClickHouse). Нормализация бизнес-ключа: `upper(trim())`; составной ключ — части через `||` в фиксированном порядке; пустой ключ (null или `''` после trim) → нулевой ключ `'0' × 32`. `hashdiff` — md5 от атрибутов в фиксированном порядке через `||`, null → `''`.
- Служебные колонки: `load_dts` — **`_extracted_at` батча**, одно значение на весь батч: по DV 2.0 это момент прихода в наш DWH. `_loaded_at` источника как `load_dts` не берём — это часы чужой базы, при перезаливке у организаторов он меняется у всех строк. `record_source` — из `_source_file`.
- **Staging** `stg_<таблица>` (view, по одной на таблицу `raw`) — единственное место жёстких правил: приведение типов (`safe_cast`, §9), `trim`, `'' → null`, хеш-ключи, `hashdiff`, `load_dts`, `record_source`. Vault читает только staging.
- **Материализация vault — `incremental`, только вставка:** хаб/линк — новые ключи, сателлит — новые `hashdiff` относительно последней версии ключа. `raw` append-only, поэтому `--full-refresh` даёт тот же результат; если за прогон пришло несколько батчей, макрос `sat` схлопывает подряд идущие одинаковые `hashdiff`.
- **Макрос `sat` (`dbt/macros/sat.sql`):** каждая строка пачки сравнивается с предыдущей версией того же ключа (`lag(hashdiff)` по `load_dts`), первая строка пачки — с последней версией в сателлите. Пример: `shipped` (д1), `delivered` (д2), `delivered` (д3, перезаливка) → в сателлите `shipped → delivered`, дубль отброшен. Отказались от «последняя строка пачки против сателлита» (`row_number() = 1`): при `--full-refresh` весь `raw` — одна пачка, от истории осталась бы одна версия на ключ, SCD2 в `dds` опустел бы. С CDC макрос не меняется. Проверено 28.10 на DWH: ежедневные прогоны и `--full-refresh` дают одинаковые таблицы (EXCEPT в обе стороны — 0).
- **Record tracking satellite `rts_*` (`dbt/macros/rts.sql`):** «в батч `load_dts` ключ был в источнике», без атрибутов, строка на ключ × батч. Источник — снимок ключей (§4.2). Все загрузки видны в vault, атрибуты не дублируются: сателлит хранит изменения, `rts` — факт присутствия, `raw` — полные строки. Отказались от сателлита без схлопывания: он равен копии `raw`, а схлопывание всё равно пришлось бы писать в каждом измерении `dds`.
- **Effectivity satellite `eff_*` (`dbt/macros/eff_sat.sql`):** `is_deleted` из `rts` — ключа нет в снимке, а раньше был → `true`, вернулся → `false`; хранятся только смены признака. Так vault, где ничего не удаляется, фиксирует удаление как событие в истории. Soft delete по контракту приходит обычным путём (атрибут статуса); `eff_*` страхует от hard delete. С CDC источником признака станут события `op = 'd'`, модель не меняется. `dds` берёт живые записи по последней версии `eff_*` или показывает флаг удаления.
- **Multi-active сателлит:** `hashdiff` — по всему набору строк родителя (строки по `payment_sequential`); изменилась или пропала любая строка → вставляется новый набор целиком.
- Только вставка: хаб/линк — новые ключи, сателлит — новые версии по `hashdiff`.
- Пустой бизнес-ключ → нулевой ключ, строки не теряем (сейчас нужен: 610 товаров без категории). Нулевой ключ — строка в хабе. Ghost-строки в сателлитах нужны только для PIT — появятся вместе с ним (§15), иначе сверка raw = ods получает лишнюю строку в каждом сателлите.
- Хаб, линк и сателлит собираются **своими** макросами dbt (`hash_key`, `hub`, `link`, `sat`, `rts`, `eff_sat`) — по одному паттерну, каждый объяснит любой в команде. Готовые пакеты (AutomateDV) — нет: чёрный ящик на защите.
- **Одна таблица источника → свои объекты vault, без джойнов источников между собой при загрузке.** Хаб пополняется из каждой таблицы, где встречается его бизнес-ключ (`hub_order` — из orders, order_items, order_payments, order_reviews); связь двух ключей — линк из той таблицы, где они лежат вместе. Так каждая таблица грузится независимо, опоздавшие строки не теряются, сверка raw ↔ vault идёт 1:1 по каждой таблице.
- **Один хаб — один тип бизнес-ключа.** Другой идентификатор той же сущности из другой системы — свой хаб + линк к основному (или same-as link, если ключи одного типа внутри одного хаба).
- Сателлиты делятся по источнику и по скорости изменения атрибутов.
- Бизнес-правила живут в `dds` (маппинги — seeds dbt), тесты dbt проверяют, что правила соблюдены.

## 9. Качество данных

- **Строки не выкидываем:** проблемы помечаются флагами в `dds`, иначе не сойдутся сверки «ничего не потеряли».
- **Тесты dbt:** `unique` / `not_null` на хеш-ключах, `relationships` линк → хаб и факт → измерение, `accepted_values` на статусах (`severity: error`); бизнес-аномалии — `warn`.
- **Сверки (singular tests):** число строк raw = ods = dds по каждой сущности; суммы между уровнями заказа и позиции; `rts_*` = число различных пар (ключ, батч) в `raw.<таблица>__keys`.
- **Уникальность версии:** в сателлите (ключ, `load_dts`) уникальны (`dbt_utils.unique_combination_of_columns`, `error`). Два разных `hashdiff` у ключа в одном батче — это multi-active данные в обычном сателлите, порядок `lag` был бы случайным.
- **Регрессия по контрольным цифрам** из `tasks.md` — как тесты; после вброса старые ответы обязаны не сдвинуться.

**Мусор в данных: строки не изымаем, публикацию блокируем**
- Макрос `safe_cast` в staging: `pg_input_is_valid(значение, тип)` (PG 16) → приводим; не приводится → null. Исходный текст остаётся в `raw`.
- Каждый сбой попадает в `ods.err_cast` (таблица, бизнес-ключ, колонка, исходное значение, `batch_id`) — это error mart DV 2.0: карантин **значений**, а не строк. Модель пересчитывается от staging.
- Тесты на `err_cast` по критичности колонки. Ключи, деньги, дата покупки, статус (`price`, `freight_value`, `payment_value`, `order_purchase_timestamp`, `order_status`) → `error`: `dbt build` падает, `dds` / `mart` / ClickHouse не обновляются, витрины остаются на прошлой консистентной версии. Остальные колонки → `warn`.
- Пустой бизнес-ключ → нулевой ключ; ключ необычного формата (не 32 hex) — тест `warn`, ключ остаётся как есть.
- Исправление: расширяем правило приведения (например, новый формат даты) → `dbt build` → значение приводится, запись из `err_cast` уходит, в сателлите появляется новая версия (`hashdiff` изменился) — исправление видно в истории.
- **Почему не карантин строк:** (1) по DV 2.0 raw vault принимает 100% данных, отбраковка — дальше по цепочке; (2) изъятый заказ тянет за собой позиции и платежи — выручка тихо уменьшится, сверка raw = ods сломается; (3) у строки с одной битой датой остальные поля верные. Блокировка публикации даёт то, что ждём от карантина (плохие цифры не уходят к аналитикам), без потери строк.
- На текущих данных: 0 неприводимых значений во всех типизируемых колонках (проверено на `source`); null'ы легитимные (нет даты вручения у недоставленных, 610 товаров без категории и габаритов).

## 11. Реакция на вброс

1. `raw`: новая таблица / колонки — только добавляем (schema drift в EL).
2. Профилирование: ключ, зерно, совпадение ключей с существующими хабами.
3. Тип источника → изменение в vault: новые атрибуты → новый сателлит; новая сущность → хаб + линк; события → линк + multi-active сателлит; другие ключи той же сущности → same-as link.
4. `ods` меняется только аддитивно; противоречия источников — разные сателлиты, приоритет решается в `dds`.
5. `dds`: новые колонки измерений / новые измерения / новый факт со своим зерном; общие измерения переиспользуются.
6. Регрессия: контрольные цифры не сдвинулись; сверка raw ↔ vault по новому источнику.
7. `mart`: новые витрины. Сборка с нуля — по-прежнему одной командой.

Вероятный кандидат: девятый файл Olist `olist_geolocation_dataset.csv` (1 млн строк, индекс → координаты), организаторы его не выдали. Ложится как `hub_zip` + сателлит с координатами + линки на адреса.

## 15. Стратегия развития (для финальной записки)

**Технологические этапы**

| Этап | Когда | Стек |
|---|---|---|
| 1 — сейчас | десятки ГБ, несколько аналитиков | Postgres + dbt + Airflow, батч-EL |
| 2 — много потребителей | десятки пользователей BI, сервисы на витринах | ClickHouse как serving-слой; reverse ETL в операционные системы |
| 3 — большие объёмы | сотни ГБ+, один узел Postgres не тянет трансформации | Cloudberry / Greenplum (PG-совместим → SQL модели переносится почти без изменений); raw-лендинг в S3 + Iceberg |

**CDC:** источник станет живым OLTP с ключами → логическая репликация / логическое декодирование в `raw` (без Kafka) → несколько потребителей изменений → **Debezium + Kafka**. Сейчас не делаем: данные статичны, в источнике нет PK (UPDATE/DELETE без `REPLICA IDENTITY` не реплицируются), DDL не реплицируется (ломается на вбросе «изменился формат»), а батч воспроизводим. Историю изменений уже даёт snapshot-diff в сателлитах.

**Продовый источник: контракт и переход на CDC.**
- Контракт с бэкендом (до CDC): PK у каждой таблицы, `updated_at` по триггеру (+ индекс), только soft delete, миграции expand → contract с ревью DWH (CODEOWNERS на папке миграций), контрактные тесты в CI бэкенда. Читаем с реплики, все таблицы — в одной транзакции `REPEATABLE READ READ ONLY` (один снимок, позиции не опережают заказ), `statement_timeout`, выгрузка порциями. `raw` — `text`, чтобы смена типа в миграции не роняла EL.
- Что `updated_at` не даёт: промежуточные состояния между прогонами, hard delete (страхует `eff_*` по снимку ключей).
- CDC закрывает это и гонку длинных транзакций, но не «из коробки»: TOAST (неизменённое большое поле приходит заглушкой → `REPLICA IDENTITY FULL` или подстановка прошлого значения), `decimal.handling.mode=string`, TRUNCATE по умолчанию пропускается, новые таблицы — в publication. Доставка at-least-once → загрузка идемпотентна (повтор даёт тот же `hashdiff`); порядок только внутри ключа; sink в `raw` — только append (upsert уничтожает историю); слот держит WAL, если Debezium лежит → `max_slot_wal_keep_size`, мониторинг лага, failover-слоты PG17. Контракт по миграциям остаётся: DDL не реплицируется.
- Модель к CDC готова: `sat` обрабатывает несколько версий ключа за прогон, служебные колонки CDC в `raw` заложены, `eff_*` переключается на `op = 'd'`. Переход: слот → начальный снимок от его позиции → оба EL параллельно → старый выключаем; пересечение схлопывает `hashdiff` (тот же `record_source`).

**PII (real-life сценарий):** в выгрузке персональных данных нет, в реальном маркетплейсе будут. Вертикальное партиционирование: публичная часть в `dds`, чувствительная — в отдельной схеме 1:1 по ключу с отдельной ролью; в общих слоях — только хеш (sha256 с солью); PII не уезжает в ClickHouse.

**Логическая структура:** новые источники (второй платёжный провайдер, логистика, CRM) → новые хабы / линки / сателлиты в `ods`; при росте — PIT / bridge для производительности, business vault для общих правил.

**PIT — регулярные, по расписанию Airflow.** Сейчас PIT нет (§6): одна загрузка, одна версия на ключ. Первым появится `pit_order` — когда у заказов накопится история (вторая загрузка с изменениями: вброс «данные поменялись» или живой источник). Его сателлиты: `sat_order` (неизменное при оформлении), `sat_order_status` (статус и даты этапов), `sat_order_payment` (multi-active, указатель на набор). Из него собирается `fct_order` — накопительный снимок «заказ на дату». Дальше — когда у хаба становится ≥2 сателлитов из разных источников (покупатель: адрес из заказов + лояльность + примерочная; товар: каталог + контент + эмбеддинги), у него появляется свой PIT.
- Отдельная задача в DAG после загрузки vault и до `dds`: снимок на дату `snapshot_dts` (ежедневно); инкрементально — добавляется новая дата, старые не пересчитываются.
- Хранение: ежедневные снимки за N дней + снимок на конец месяца бессрочно.
- Что даёт: (1) модели `dds` джойнят сателлиты по равенству указателей, а не пересчитывают `row_number()` по всей истории каждого сателлита; (2) воспроизводимость отчёта «на дату»: звезда, собранная из PIT на дату X, показывает ровно то, что показывал отчёт в день X, даже если источник с тех пор поменял данные.
- Отсутствие версии на дату → указатель на ghost-запись, чтобы джойн никогда не терял строки.

**Business vault — когда у правила появляется второй потребитель вне звезды** (ML-фичи, reverse ETL, поисковый индекс, агенты). Тогда правило переезжает из `dds` в вычисляемый сателлит `bsat_*` (отдельная схема `bv`):
- dbt-модели поверх raw vault, те же макросы `sat` (hashdiff, insert-only), `record_source = 'bv.<правило>'` — видно, что это вычисление, а не источник.
- Маппинги правил — seeds dbt (статус → группа, штат → регион, нормализация городов); тесты dbt проверяют их полноту (каждый статус источника попал в группу).
- Первые кандидаты: группа статуса заказа, нормализованный город/штат продавца, флаги качества заказа; с новыми источниками — атрибуция заказа к видео / поисковой сессии, конверсия бонусов в рубли выручки.
- `dds` после этого читает правила из `bv`, а не считает их сам — у всех потребителей одна и та же цифра.

**Bridge — когда удлинятся цепочки линков.** Сейчас факт собирается из своего линка плюс один-два джойна. Bridge появится, когда (1) зерно факта проходит через 3+ линка (видео → товар → продавец → заказ; бонусная операция → заказ → профиль → покупатель) и (2) `dds` переходит на инкрементальную сборку. Bridge — снимок цепочки хеш-ключей на `snapshot_dts`, строится той же задачей Airflow, что и PIT; факт = bridge + указатели PIT.

**Частичная сборка dbt — когда полный build станет долгим.** Сейчас собираем только полным `dbt build` (весь граф ≈ 1 мин, так же работает DAG). Частичный селектор `+path:models/mart` небезопасен: dbt-postgres пересоздаёт таблицу через `DROP … CASCADE`, и view, которых нет в выборке (`fct_payment__active` поверх `fct_payment`), пропадают; следом падает `dds_reconcile`. Когда сборка вырастет до десятков минут: штатная частичная команда — `@`-селектор (захватывает соседних потомков пересобираемых таблиц), либо `__active` материализуются таблицами; при переходе `dds` на инкрементальную сборку вопрос снимается вместе с полной пересборкой таблиц.

### Новые источники и сервисы (план развития — сейчас не реализуем)

Маркетплейс будет обрастать сервисами: программа лояльности, короткие видео, виртуальная примерочная, AI-агенты поиска товаров. Ниже — как на это реагирует система и что делаем мы. Модель рассчитана на то, что существующее при этом **не переделывается**.

**Как ведёт себя система**
- `raw`: новый источник → новые таблицы; новые колонки старого источника доезжают сами (schema drift в EL). Существующие таблицы не трогаются.
- `ods`: только добавление — новые хабы / линки / сателлиты. Старые объекты, их ключи и история не меняются, поэтому старые отчёты и контрольные цифры не сдвигаются.
- `dds`: общие измерения (`dim_customer`, `dim_product`, `dim_seller`, `dim_date`) переиспользуются; новый процесс — новый факт со своим зерном; новые атрибуты — новые колонки измерений.
- Если упал тест dbt по новому источнику, downstream не запускается: витрины остаются на прошлой консистентной версии.

**Наши действия при подключении источника** (общий порядок — как при вбросе, §11, плюс то, что нужно для живого сервиса)
1. **Контракт с командой сервиса:** что за сущности, бизнес-ключи, зерно, частота и способ выгрузки (батч / CDC), ожидаемый объём, есть ли PII.
2. **Идентичность:** каким ключом сервис опознаёт покупателя / товар / продавца. Совпадает с нашим бизнес-ключом → линк на существующий хаб. Свой id → свой хаб + линк к основному (как `hub_customer_profile` → `hub_customer`).
3. **Класс объёма:** справочники и транзакции — в Postgres через vault; клик-стрим (миллионы событий в день) — мимо vault в S3 / Iceberg или ClickHouse, в vault только сущности и дневные агрегаты.
4. **Класс данных:** PII и биометрия — в отдельную зону (§15, PII), в общих слоях — только хеш или ссылка.
5. **Vault:** хабы, линки, сателлиты по правилам §6; события — non-historized link; у хаба стало ≥2 сателлитов → свой PIT в расписании Airflow.
6. **Правила:** новое правило, нужное нескольким потребителям, → сразу в business vault.
7. **dds / mart:** новые факты и колонки измерений, витрины под вопросы сервиса.
8. **Качество:** тесты ключей и связей, сверка raw ↔ vault по новому источнику, регрессия старых контрольных цифр.

**Сценарии**

| Сервис | `ods` | `dds` | На что влияет |
|---|---|---|---|
| Программа лояльности | `hub_loyalty_member` + линк на `hub_customer`; начисления и списания — линк с `hub_order`; уровень участника — сателлит с историей | `dim_customer` SCD2 с уровнем; `fct_loyalty_txn`; бонусы — новый способ оплаты в `fct_payment` | первый PIT на `hub_customer`; списание бонусов — выручка или скидка: правило для BV, иначе разойдётся выручка; баланс бонусов полуаддитивен — по времени не суммируется |
| Короткие видео | `hub_video`; линки видео ↔ товар, видео ↔ автор (продавец / покупатель); сателлит с метаданными | `dim_video`, `fct_video_daily`; атрибуция видео → заказ | просмотры — клик-стрим, в vault не грузим, только агрегаты; правило атрибуции (окно, last-touch) — BV; длинная цепочка видео → товар → заказ — первый bridge |
| Виртуальная примерочная | `hub_tryon_session`; линк сессия × покупатель × товар; сателлит с результатом (размер, «подошло»); согласие на обработку фото — отдельный сателлит | `fct_tryon`, конверсия примерки в заказ, влияние на возвраты | **фото — биометрия (LGPD):** в DWH не храним, только ссылку на объектное хранилище в PII-зоне с TTL; без согласия — не используем |
| AI-агенты поиска («найди подарок») | логи агента: `hub_search_session`; линк сессия × товар (показан / выбран) × заказ; сателлит с запросом | `fct_agent_session`, конверсия «запрос → покупка» | агент — прежде всего потребитель данных о товарах, источником становятся его логи |

**Поиск товаров для агентов**
- Поисковый индекс — **копия для выдачи, а не источник правды**: пересобирается из DWH, как ClickHouse. Цепочка: `mart.product_search_doc` (товар, категория EN, цена, рейтинг по отзывам, рейтинг продавца, прогноз срока доставки из `ml`) → задача Airflow: эмбеддинги → индекс.
- Этап 1 — **pgvector** в нашем Postgres: без новой инфраструктуры, векторный поиск вместе с SQL-фильтрами (цена, штат, срок доставки).
- Этап 2 — **OpenSearch / Elasticsearch**: когда в каталоге миллионы товаров, нужен гибрид BM25 + kNN, фасеты, португальская морфология, и боевой трафик надо отделить от DWH.
- Ограничение данных: в Olist нет названий и описаний товаров (только длины), поэтому семантический поиск появится с новым источником каталога — это новый сателлит на `hub_product` и повод для PIT по товару. Эмбеддинги — производные данные: в `ml` / `bv`, не в raw vault.

**Версии измерений в проде.** Факт ссылается на версию измерения на момент поступления в DWH (Kimball SCD2 + Type 7, [dds-spec §20](dds-spec.md)). Чем чаще обновляется DWH (часовые батчи → CDC), тем точнее `load_dts` совпадает с реальным моментом изменения — в проде это минуты, и SCD2 по `load_dts` даёт историю «как было на момент события». То же правило присваивает SK при инкрементальной загрузке фактов, поэтому переход `dds` на инкремент не меняет цифр.

**Узкие места:** полная перезаливка → инкремент по водяному знаку / CDC; пересборка `dds` целиком → инкрементальные модели dbt; конкурентные запросы BI к Postgres → ClickHouse.

## 16. Использование ИИ

Ведём журнал: что спросили, что приняли, что отвергли и почему, как проверили. Уже зафиксировано:

Приняли D: A теряет историю при `--full-refresh`, C дублирует `raw`. Проверили на DWH: инкрементальные прогоны по дням и `--full-refresh` дают одинаковые `sat` / `rts` / `eff` (28.10).
- Контрольная выручка, «грабли» данных и запас обещанного срока доставки — проверены скриптами на данных, не взяты на веру.
