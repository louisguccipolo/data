# Marketplace DWH — спецификация проекта (хакатон RWB)

> Хакатон: 1 день, 09:00–21:00. Команда 5 человек.
> Статус: черновик по итогам интервью 27.10.2026. Моделирование core и витрин **не начато** — ждёт список дашбордов от аналитика.

---

## 1. Цель

Построить DWH маркетплейса, который:
1. принимает данные из OLTP бэкенда (или датасета организаторов / открытого датасета);
2. моделирует их по Kimball (звезда, снежинка там, где есть иерархии) в MPP (Apache Cloudberry);
3. отдаёт витрины в ClickHouse для дашбордов, кабинета продавца и ML;
4. показывает «горячие» метрики за сегодня через микробатч OLTP → ClickHouse;
5. разграничивает чувствительные данные покупателей и продавцов (вертикальное партиционирование).

Жюри (предположительно) оценивает всё сразу: инженерную часть DWH, бизнес-инсайты, продукт и демо. Поэтому ни одно из направлений не проседать до нуля.

## 3. Архитектура

```
                    ┌──────────────── batch (@hourly / по кнопке) ────────────────┐
                    │                                                             ▼
 OLTP Postgres ──EL (COPY, updated_at)──► Cloudberry raw ─► stg ─► core (Kimball) ─► mart ──EXCHANGE──► ClickHouse mp.*  (история до вчера)
  ▲      │                                  (append-only)  │ dbt         │ SCD2, snapshots           │
  │      │                                                 └► quarantine └► pii (отдельно, роли)     ├─► dictionaries (dims) ─┐
  │      └──── микробатч */2 мин (Airflow) ──► ClickHouse hot.* (ReplacingMergeTree, только «сегодня»)│                        │
  │                                                                                                   ▼                        ▼
  │                                                                      mp.v_* = UNION ALL(история, сегодня) + dictGet ─► BI / кабинет продавца (API бэкенда)
replay (датасет со сдвигом времени)                                                    ml.* ◄── батч-скоринг (Airflow) ◄── mart/feature snapshots
```

**Принципы**
- ELT: трансформации в Cloudberry через dbt. Spark и S3 не используем (S3/MinIO — только если данные придут файлами и выберем lakehouse-landing, см. §4).
- ClickHouse — serving-слой: только витрины, **никакого PII**.
- Горячий путь и батч **разделены по времени**: батч отвечает за всё до вчера включительно, горячий — только за сегодня. Цифры не пересекаются → нет вопроса «почему GMV не сходится».
- Атрибуты измерений в горячем пути берутся из **ClickHouse dictionaries на core-измерениях DWH** → одна версия истины для названий/категорий/регионов.

## 4. Источники данных — три сценария

| Сценарий | Что делаем |
|---|---|
| **A. Организаторы дают данные в домене маркетплейса** (заказы, товары, продавцы…) | Маппим в OLTP-схему → пайплайн без изменений. |
| **B. Данные вне домена / сырые файлы** | Решаем по факту: либо маппинг в OLTP, либо landing в MinIO → raw (lakehouse-вариант). Готовность: оба загрузчика как опция. |
| **C. Данных не дают** | **Olist** (Brazilian E-Commerce, ~100k заказов 2016–2018: заказы, позиции, платежи, отзывы, продавцы, товары, обещанная и фактическая дата доставки) → маппинг в OLTP + **replay**. |

Открытых датасетов WB/Ozon с заказами/выкупом **нет** (WB в 2025 закрыл даже остатки; продажи доступны только продавцу через свой токен API) — проверено поиском.

Генерацию синтетики **не используем** как основной источник (нет реального сигнала для ML, скучные дашборды). Если данных мало — допустим переход DWH на Postgres, но предпочтительно оставаться на MPP.

### 4.1 Replay (живой поток из статичного датасета)
- История до момента `T_split` грузится в OLTP сразу.
- Хвост датасета после `T_split` проигрывается в OLTP DAG-ом: все таймстемпы сдвигаются на `offset = now() − T_split`, со скоростью `k` (например, 1 час датасета = 1 минута реального времени).
- Replay пишет события в OLTP так, как их писал бы бэкенд: вставка заказа → обновления статусов позиций по мере наступления сдвинутых таймстемпов (`updated_at` обновляется триггером).
- Идемпотентность: replay хранит свой watermark (последний проигранный dataset-timestamp).

## 5. OLTP-схема

Текущая версия: `oltp/schema.sql` (общий маркетплейс). **Нужно переделать:**

1. **Жизненный цикл на уровне позиции заказа** (решено): `order_items` получает `status`, `warehouse_id` и таймстемпы этапов; `orders` — шапка (покупатель, оплата, адрес/ПВЗ). Плюс таблица истории статусов `order_item_status_history`. Для Olist (статус только на заказе) статус позиции выводится из статуса заказа.
2. **Опциональный WB-модуль** (включаем, если кейс в домене RWB):
   - пункты выдачи (`pickup_points`), статусы «прибыл в ПВЗ → выкуплен / отказ → возврат продавцу»; **выкуп считается по позиции**;
   - модель фулфилмента FBO / FBS (`fulfillment_type` на позиции/товаре), остатки по складам (`stocks`);
   - юнит-экономика продавца: комиссия по категории, логистика, хранение, штрафы, сумма к перечислению.
3. Правила, которые уже заложены и сохраняются: PK + `updated_at` (триггер) у каждой таблицы; soft delete; enum = `text + CHECK`.

**Контракт схемы:** черновик делает DE, бэкенд ревьюит; **согласование до 11:00**. После — только аддитивные изменения (новые колонки/таблицы), без rename/drop/смены типа; изменения через миграции в общем репо. Raw-слой подхватывает новые колонки автоматически.

## 6. Слои DWH (Cloudberry)

| Схема | Содержимое | Доступ |
|---|---|---|
| `raw` | append-only копия OLTP, все версии строк, `_loaded_at`; AO column zstd, `DISTRIBUTED RANDOMLY` | только ETL (содержит PII) |
| `stg` | views: дедуп последней версии, типы, чистка | только ETL (содержит PII) |
| `quarantine` | строки, не прошедшие DQ-правила, с причиной | ETL, аналитик (без PII) |
| `snapshots` | dbt snapshots (SCD2), только публичные атрибуты | ETL |
| `core` | Kimball: `dim_*`, `fct_*`, periodic snapshots | analyst |
| `pii` | вертикально отрезанные чувствительные атрибуты, 1:1 по natural key | pii_officer |
| `mart` | широкие витрины под ClickHouse | analyst, ch_reader |
| `ml` | фичи-снапшоты (если не в mart) и предсказания | analyst, ML |

Уже реализовано в `dwh/init.sql`: схемы, роли `analyst` / `pii_officer` / `ch_reader` / демо-логины, default privileges.

### 6.1 Соглашения Cloudberry
- Факты: `appendoptimized=true, orientation=column, compresstype=zstd`, `DISTRIBUTED BY` по ключу самого частого джойна (обычно `order_id`).
- Маленькие измерения: `DISTRIBUTED REPLICATED` (без redistribute motion при джойнах).
- Инкременты: `delete+insert` (MERGE в Cloudberry нет — ядро PG14).
- Макрос `postgres__create_table_as` уже переопределён: dbt-конфиги `distributed_by` (`'<col>' | 'randomly' | 'replicated'`) и `storage`.

## 7. Моделирование (Kimball) — правила, без конкретных моделей

> Конкретные факты/измерения проектируются **после** списка дашбордов от аналитика: дашборды → витрины → нужные факты и измерения → bus matrix. Строятся в dbt снизу вверх: витрины всегда `ref()` на core, никогда на stg.

- **Conformed dimensions**: одно `dim_customer`, `dim_seller`, `dim_product`, `dim_date`, `dim_geo` на все факты.
- **Снежинка — только для иерархий**: дерево категорий, гео (outrigger, общий для покупателя / продавца / склада / ПВЗ). В ClickHouse — всегда плоско (OBT).
- **SCD2** для покупателя и продавца через dbt snapshots, `strategy='check'` на отслеживаемых атрибутах (не на любом апдейте). Первая версия открыта с `1900-01-01`, чтобы покрыть факты до первого снапшота.
- **Суррогатные ключи (решено):** `bigint` из хеша — 64 бита от `md5(natural_key || valid_from)`; детерминированы, считаются на сегментах параллельно, дешёвые в джойнах и ClickHouse. Тест `unique` на каждом SK. Нужен dbt-макрос `hash_sk(...)`.
- **Accumulating snapshot** жизненного цикла — на зерне **позиции заказа** (создан → оплачен → отгружен → в ПВЗ → выкуплен/отказ/возврат), с длительностями этапов.
- **Periodic snapshots как замена PIT из Data Vault** (решено): `покупатель × день`, `продавец × день`, `товар × день` с накопительными метриками **по времени события-исхода** (`resolved_at`, а не `created_at`). Факт заказа джойнится со снапшотом **за предыдущий день** → фичи без утечки. Те же таблицы закрывают прогноз спроса (зерно `товар × день`) и динамику в кабинете продавца.

## 8. Чувствительные данные (PII)

- Вертикальная партиция: публичная часть в `core.dim_*`, чувствительная — `pii.customer_pii` / `pii.seller_pii` (1:1 по natural key). В `core` — только `email_hash` (sha256 с солью) для джойнов/дедупа.
- Покупатель: ФИО, email, телефон, дата рождения (в публичной части — год рождения / возрастная группа). Продавец: юр. название, ИНН, расчётный счёт, контакты.
- PII не уезжает в ClickHouse и не попадает в snapshots.
- Демо: под `analyst_user` `SELECT` из `pii.*` → `permission denied`; под `dpo_user` — ок.
- **Открыто:** в Olist PII нет. Досинтезировать ли детерминированные ФИО/email/ИНН поверх реальных id — **решаем на месте**.

## 9. Качество данных (решено: карантин строк)

- Плохие строки **не валят пайплайн**, а уходят в `quarantine.<entity>` с колонками `_dq_rule`, `_dq_reason`, `_detected_at`; в core проходят только валидные.
- Правила проверяются на уровне stg (например: цена < 0, позиция без заказа, неизвестный статус, дата в будущем).
- Тесты dbt остаются: PK/FK/not_null на core и mart — `severity: error` (если упали после карантина — это баг модели, блокируем загрузку в ClickHouse; витрины остаются на прошлой консистентной версии благодаря `EXCHANGE`). Бизнес-аномалии — `warn`.
- `dbt source freshness` на raw. Итоги DQ (кол-во строк в карантине по правилам) — витрина для дашборда качества.

## 10. ClickHouse

- Витрины `mp.*`: `MergeTree`, `PARTITION BY toYYYYMM(date)`, `ORDER BY` под фильтры дашбордов, `LowCardinality(String)` для справочных строк.
- Загрузка из Cloudberry: `TRUNCATE mp.<t>__stg` → `INSERT … SELECT FROM postgresql(cloudberry_dwh, …)` → сверка count → `EXCHANGE TABLES`. Для больших фактов — `REPLACE PARTITION`. Реализовано в `pipelines/mart_to_clickhouse.py` (список `MARTS` пуст до моделирования).
- Креды к Cloudberry — в named collection `cloudberry_dwh` (пароль не светится в query_log). Связка проверена.
- **Горячий слой** `hot.*`: `ReplacingMergeTree(updated_at)`, только строки за сегодня; чтение с `FINAL`.
- **Словари** на core-измерениях из Cloudberry (`LIFETIME` ~5 мин). Новый сегодня товар/продавец до следующего батча → `unknown`.
- **Единые view** `mp.v_*` = `UNION ALL` (батч `< today()` + горячий `= today()`) + `dictGet` для атрибутов.
- Read-only пользователь `bi` для BI (реализовано).

## 11. Горячий путь (микробатч)

- **Оркестрация (решено): отдельный Airflow DAG `hot_path`, расписание `*/2 * * * *`, `max_active_runs=1`** — ради единого мониторинга. Запасной вариант, если Airflow не тянет частоту: refreshable materialized view в ClickHouse (`REFRESH EVERY 1 MINUTE`, читает окно «сегодня» из OLTP через `postgresql()`).
- Инкремент по `updated_at` из OLTP за сегодня → `INSERT` в `hot.*`; дубли схлопывает ReplacingMergeTree.
- Граница «сегодня» — по одной таймзоне (UTC или MSK — зафиксировать одну на весь проект). При replay «сегодня» — это сдвинутое время.
- Не используем: PostgreSQL engine вживую (нагружает OLTP каждым рефрешем дашборда), MaterializedPostgreSQL (экспериментальный), Debezium + Kafka (overkill).

## 12. ML

Кандидаты от ML-инженера: прогноз спроса, прогноз срока доставки, вероятность выкупа по позиции, вероятность плохого отзыва, антифрод возвратов. **Обязательна одна модель**, выбор зависит от данных (на Olist естественны срок доставки и плохой отзыв; выкуп — только при WB-данных).

- **Serving (решено): всё батчем.** Задача Airflow скорит активные позиции/товары → `ml.predictions_<task>` → витрина → ClickHouse → кабинет продавца.
- **Фичи (решено): смешанно.** DE делает общие point-in-time агрегаты (periodic snapshots из §7, SCD2 as-of). Специфичные фичи — ML.
- Правило против утечки: фича для объекта с временем `t` использует только события с `resolved_at < t` (на практике — снапшот за день до `t`).
- Контракт предсказаний (на каждую задачу): `entity_id, score/prediction, model_version, scored_at`; витрина берёт последний `scored_at`.

## 13. BI и кабинет продавца

- BI: аналитик планирует **Tableau**, но инструмент может поменяться. ClickHouse остаётся в любом случае. Запасные: **DataLens** (Yandex), Metabase. Если у выбранного BI нет коннектора к ClickHouse — пишем коннектор/выгрузку.
- **Кабинет продавца**: фронт → API бэкенда → параметризованные запросы к ClickHouse; **изоляция по `seller_id` из токена на уровне API** (решено). Метрики: продажи, выкуп, возвраты, рейтинг, срок доставки, прогнозы ML.

### 13.1 Кто какой слой читает (решено)

| Слой | Потребители | Роль |
|---|---|---|
| **Cloudberry `mart`** | аналитики, ML, другие команды, BI для ad-hoc | общие **data products** под контрактом (`contract: enforced`, версии моделей dbt); источник правды |
| **ClickHouse `mp`** | BI-дашборды, **API кабинета продавца** | serving-копия части витрин, разложенная под паттерны доступа |

**Бэкенд в Cloudberry не ходит.** Причины:
- MPP плохо держит высокую конкурентность мелких запросов: каждый запрос уходит через координатор на все сегменты, а соединений на координаторе мало;
- dbt пересобирает таблицы через `RENAME`, которому нужна эксклюзивная блокировка, а тяжёлые трансформации занимают сегменты. Получится, что ETL тормозит пользовательский сервис;
- связанность: изменения в DWH ломали бы продовый API.

**Правила serving в ClickHouse для API:**
- отдельные витрины под API `api_*`, отсортированные под фильтр бэкенда: `ORDER BY (seller_id, date)` / `(seller_id, order_ts)`, агрегаты — на `AggregatingMergeTree`. Общие OBT, отсортированные по дате, бэкенд не читает;
- контракт с бэкендом — именно набор `api_*`, а не «любой SQL»;
- отдельный пользователь ClickHouse для бэкенда: `readonly`, квота, `max_execution_time`, лимит одновременных запросов (изоляция от тяжёлых запросов BI);
- в UI кабинета показываем свежесть данных: история приходит батчем, сегодняшний день — горячим путём (≤2 мин), ML — с частотой скоринга.

**Stretch:** reverse ETL готовых агрегатов по продавцу в OLTP Postgres, чтобы бэкенд читал только свою базу. Делаем, если останется время (см. §17).
