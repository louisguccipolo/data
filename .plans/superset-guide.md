# Capibara: спецификация витрин ClickHouse и гайд по Superset

Документ для команды хакатона. Это проект витрин и инструкция; таблицы, DAG и Superset этим документом не создаются. Имена полей предлагаемой модели нужно сопоставить с фактическим `core` команды.

## 1. Область первой версии

Один дашборд «Capibara: продажи и покупатели», отвечающий на пять вопросов блока А. Аудитория — руководитель маркетплейса и аналитик: динамика продаж, ведущие продавцы и категории, размер заказа, повторные покупки.

Источники: восемь CSV Olist, 550 759 строк. Контрольные значения ниже воспроизведены на локальной выгрузке. Витрины строятся из `core`, не напрямую из `raw`.

**Принятые определения:**

| Показатель | Правило |
|---|---|
| Выручка в терминологии задания | Сумма `price` по позициям заказов со статусом `delivered`, без доставки. Это стоимость товаров, а не собственный доход площадки. |
| Чек заказа | Сумма `price + freight_value` всех позиций одного доставленного заказа. |
| Средний чек | Общая сумма чеков / количество доставленных заказов. |
| Единицы товара | Число исходных позиций: в CSV одна строка соответствует одной единице. |
| Строки заказа | Число исходных позиций до возможного объединения одинаковых товаров в `core`. |
| Покупатель | Уникальный `customer_unique_id`, а не `customer_id`. |
| Повторный покупатель | Человек с двумя и более заказами во всей выгрузке, независимо от статуса. Именно это воспроизводит 3,12%. |
| Категория | Исходная категория товара; отсутствие категории — отдельная группа. Отсутствие перевода не означает отсутствие категории. |
| Месяц | Месяц `order_purchase_timestamp`. Это принятое правило для первой версии. |

Первая задача: `[2016-09-01, 2018-09-01)` по дате оформления. Остальные четыре: вся выгрузка. Для доставленных заказов в этой выгрузке ограничение первой задачи не меняет общий итог, но для покупателей такое равенство не предполагается.

Число заказов в месячном отчёте трактуем как число доставленных заказов; рядом сохраняем число всех оформленных заказов. Это открытое бизнес-решение, поскольку отдельного контроля количества заказов в задании нет. Подписи графиков должны явно различать эти числа.

## 2. Общий контракт

- `mart` — предлагаемое имя базы данных ClickHouse для витрин. Это не PostgreSQL-схема.
- Деньги: `Decimal(18,2)`; агрегаты могут иметь более широкий Decimal-тип. Не использовать Float для промежуточных денежных сумм.
- Количества: `UInt64`; месяц: `Date`; идентификаторы: `String`.
- Средние и доли считать из числителя и знаменателя, округлять только при отображении.
- У каждой публикуемой таблицы одна текущая версия данных. Повторный запуск DAG заменяет её, а не дописывает те же агрегаты.
- Для физических таблиц допустим `MergeTree` с ключом сортировки, указанным ниже. `ORDER BY` не обеспечивает уникальность: проверять её отдельно. Не использовать фоновое слияние как единственную защиту от дублей.
- Если `core` пока статичен, обычные VIEW также возможны. При материализации Airflow должен явно пересобирать витрины после изменения источников.
- Все связи позиций с заказами, товарами и продавцами проверять до расчёта. Платежи и отзывы не присоединять к позициям для этих пяти задач.
- Сохранить `source_item_count`, если в `core` несколько исходных позиций объединяются в строку с `quantity`. Ниже `line_count` и `unit_count` должны сохранить смысл исходных данных.

## 3. Витрины

### 3.1. `mart.monthly_sales`

**Гранулярность:** один календарный месяц. Ровно 24 строки. Ключ сортировки: `month`.

| Поле | Тип | Правило |
|---|---|---|
| `month` | Date | Первый день месяца. |
| `orders_all_count` | UInt64 | Все заказы, оформленные в этом месяце, включая заказы без позиций. |
| `orders_delivered_count` | UInt64 | Заказы со статусом `delivered`, оформленные в этом месяце. |
| `revenue_amount` | Decimal | Сумма стоимости товаров доставленных заказов. |

Сначала создать календарь месяцев, затем присоединить отдельные агрегаты заказов и сумм позиций. Отсутствующие значения заменить нулями. Все заказы нельзя считать после INNER JOIN с позициями: 775 заказов в исходной выгрузке не имеют позиций.

Контроль: 24 уникальных месяца; ноябрь 2016 — нули; сумма выручки `13 221 498,11`; сумма доставленных заказов `96 478`.

### 3.2. `mart.seller_sales`

**Гранулярность:** один продавец с продажами в доставленных заказах. Ключ сортировки: `seller_id`. Хранить всех таких продавцов, не только топ-10.

| Поле | Тип | Правило |
|---|---|---|
| `seller_id` | String | Продавец позиции заказа. |
| `seller_city` | String | Город из справочника продавцов. |
| `seller_state` | String | Штат из справочника продавцов. |
| `orders_count` | UInt64 | Точное число различных `order_id` данного продавца. |
| `line_count` | UInt64 | Число исходных позиций. |
| `unit_count` | UInt64 | Число проданных единиц. |
| `revenue_amount` | Decimal | Сумма `price` только собственных позиций продавца. |

В ClickHouse использовать `uniqExact(order_id)` для контрольных distinct-подсчётов. Продавец-лидер: `4869f7a5dfa277a7dca6462dcf3b52b2`, выручка `226 987,93`.

Сумма выручки всех продавцов равна общей выручке. Сумма `orders_count` по продавцам НЕ обязана равняться числу заказов: в одном заказе бывают разные продавцы.

### 3.3. `mart.order_summary`

**Гранулярность:** одна итоговая строка по всем доставленным заказам. Ключ сортировки: `summary_key`.

| Поле | Тип | Правило |
|---|---|---|
| `summary_key` | String | Константа `delivered_all`. |
| `orders_count` | UInt64 | Количество доставленных заказов. |
| `revenue_amount` | Decimal | Общая стоимость товаров без доставки. |
| `freight_amount` | Decimal | Общая стоимость доставки из позиций. |
| `order_value_amount` | Decimal | `revenue_amount + freight_amount`. |
| `line_count` | UInt64 | Общее число исходных позиций. |
| `unit_count` | UInt64 | Общее число единиц товара. |

Сначала получить суммы на уровне одного заказа, затем итог. Не использовать среднее от `price` или от `price + freight_value` отдельных позиций.

Контроль:

- `orders_count = 96 478`;
- `revenue_amount = 13 221 498,11`;
- `freight_amount = 2 202 965,54`;
- `order_value_amount = 15 424 463,65`;
- `line_count = unit_count = 110 197`;
- средний чек `159,8754498…`, отображается `159,88`;
- среднее число строк и единиц `1,142198…`, отображается `1,142`.

### 3.4. `mart.customer_summary`

**Гранулярность:** одна итоговая строка по покупателям всей выгрузки, все статусы. Ключ сортировки: `summary_key`.

| Поле | Тип | Правило |
|---|---|---|
| `summary_key` | String | Константа `all_customers`. |
| `customers_count` | UInt64 | Число уникальных `customer_unique_id`. |
| `repeat_customers_count` | UInt64 | Число покупателей с двумя и более заказами. |
| `one_order_customers_count` | UInt64 | Число покупателей ровно с одним заказом. |
| `orders_count` | UInt64 | Общее число заказов в этой выборке. |

Алгоритм: orders → customers по `customer_id` → группировка по `customer_unique_id` → точное количество заказов на человека → итог. Не присоединять позиции: это потеряет заказы без товаров.

Контроль: `96 096` покупателей; `2 997` повторных; `93 099` с одним заказом; `99 441` заказ; доля повторных `0,031187562…`, в интерфейсе `3,12%`.

Это «покупатели с повторным заказом», а не retention по когортам и не доля повторных успешных выкупов. Фильтр статуса `delivered` здесь применять нельзя для воспроизведения контроля.

### 3.5. `mart.category_sales`

**Гранулярность:** одна исходная категория, включая отдельную неизвестную. Ровно 74 строки. Ключ сортировки: `category_key`.

| Поле | Тип | Правило |
|---|---|---|
| `category_key` | String | Исходное имя категории; для пустого значения — зарезервированный ключ `__unknown__` после проверки отсутствия коллизии. |
| `category_name_original` | Nullable(String) | Название на португальском. |
| `category_name_english` | Nullable(String) | Перевод при наличии. |
| `category_label` | String | Английский перевод; иначе оригинал; для пустой категории «Категория не указана». |
| `is_unknown_category` | UInt8 | 1 только при отсутствии исходной категории. |
| `is_translation_missing` | UInt8 | 1 при непустой категории без перевода. |
| `orders_count` | UInt64 | Точное число заказов, содержащих эту категорию. |
| `unit_count` | UInt64 | Число единиц доставленных товаров категории. |
| `revenue_amount` | Decimal | Выручка категории без доставки. |
| `revenue_share` | Float64 | Выручка категории / выручка всех 74 групп; доля 0–1. |

Фильтр заказов: `delivered`. Переводы присоединять LEFT JOIN. Сохранять две категории без перевода: `pc_gamer` и `portateis_cozinha_e_preparadores_de_alimentos`.

Контроль: 74 категории; сумма выручки `13 221 498,11`; лидер `beleza_saude` / `health_beauty` — `1 233 131,72`; сумма долей равна 1 с допуском `1e-9` до округления.

Доля фиксирована относительно всех категорий. Показ только топ-10 не должен пересчитывать их сумму до 100%. Количество заказов нельзя складывать между категориями.

### 3.6. Служебная `mart.refresh_status`

Не бизнес-витрина. Одна строка последней успешно опубликованной версии: `batch_id String`, `published_at DateTime64(3, 'UTC')`, `source_rows UInt64`, `checks_passed UInt8`.

Историю запусков и неудачи хранить отдельно или в Airflow. Не заменять дату успешного обновления временем последней неудачной попытки. `published_at` — время обновления витрин, а не дата событий 2016–2018 годов.

## 4. Обновление через Airflow

1. Прочитать источники и загрузить `raw` идемпотентно.
2. Обновить `core`, привести типы, выполнить проверки ключей и связей.
3. Собрать пять витрин в промежуточных таблицах для одного `batch_id`.
4. Проверить контрольные суммы, уникальность ключей, календарь и категории.
5. Опубликовать проверенный комплект; затем обновить `refresh_status`.
6. Обновить или инвалидировать кэш Superset либо дождаться настроенного TTL и принудительно обновить графики перед демонстрацией.

Не делать `TRUNCATE` опубликованных витрин перед успешной сборкой замены. Не публиковать пустые или частично рассчитанные результаты.

Для небольшого демо допустимо переключать таблицы в согласованное окно, когда дашборд не читают, затем обновить весь экран. Несколько переключений таблиц не следует объявлять общей атомарной транзакцией. Для постоянной работы лучше хранить версии и привязывать все запросы дашборда к одному выбранному `batch_id`.

Если выбран ReplacingMergeTree, помнить: повторная загрузка не гарантирует немедленное исчезновение дублей при обычном SELECT. Для начальной полной загрузки проще явная сборка новой версии.

## 5. Подключение Superset

Инструкция предполагает, что Superset уже развёрнут. Сначала узнать и зафиксировать версию его Docker-образа.

1. Добавить `clickhouse-connect` совместимой версии в зависимости образа Superset и пересобрать образ. Установка вручную в работающий контейнер потеряется при его пересоздании. Для официального репозиторного Compose предусмотрен `docker/requirements-local.txt`; в собственном Compose зависимости добавляются в собственный Dockerfile.
2. Superset и ClickHouse должны находиться в общей Docker-сети. У ClickHouse должен быть доступен HTTP-интерфейс внутри этой сети.
3. Подготовить пользователя `bi_reader` с правом SELECT на нужные витрины.
4. В Superset открыть **Settings → Database Connections → + Database**. В некоторых версиях названия меню отличаются. Выбрать ClickHouse либо ввод SQLAlchemy URI.
5. Ввести URI:

```text
clickhousedb://bi_reader:<URL_ENCODED_PASSWORD>@clickhouse:8123/mart
```

`clickhouse` здесь — пример имени сервиса из Compose, а не обязательное имя. Пароль со специальными символами кодируется для URL. Используется HTTP-порт 8123, не native TCP 9000. `localhost` внутри Superset указывает на сам контейнер Superset.

6. Нажать **Test Connection**, затем сохранить подключение.
7. В **SQL Lab → SQL Editor** проверить доступ:

```sql
SELECT count(), sum(revenue_amount)
FROM mart.monthly_sales;
```

Ожидается 24 строки в витрине и сумма 13221498.11.

Официальная инструкция: https://superset.apache.org/user-docs/databases/supported/clickhouse/

## 6. Регистрация датасетов и метрик

В **Datasets → + Dataset** выбрать подключение и зарегистрировать каждую из пяти витрин, затем `refresh_status`. Если интерфейс показывает поле Schema, выбрать базу `mart` там, где её предоставляет драйвер.

Для `monthly_sales` отметить `month` как временную колонку. Для карточек из summary-таблиц временную колонку не задавать.

В редакторе датасета добавить сохранённые SQL-метрики:

| Датасет | Имя метрики | SQL |
|---|---|---|
| monthly_sales | `revenue` | `SUM(revenue_amount)` |
| monthly_sales | `delivered_orders` | `SUM(orders_delivered_count)` |
| monthly_sales | `placed_orders` | `SUM(orders_all_count)` |
| seller_sales | `revenue` | `SUM(revenue_amount)` |
| seller_sales | `seller_orders` | `MAX(orders_count)` — только при группировке по одному seller_id |
| seller_sales | `units` | `SUM(unit_count)` |
| order_summary | `revenue` | `MAX(revenue_amount)` |
| order_summary | `avg_order_value` | `SUM(order_value_amount) / nullIf(SUM(orders_count), 0)` |
| order_summary | `avg_lines` | `toFloat64(SUM(line_count)) / nullIf(SUM(orders_count), 0)` |
| order_summary | `avg_units` | `toFloat64(SUM(unit_count)) / nullIf(SUM(orders_count), 0)` |
| customer_summary | `customers` | `MAX(customers_count)` |
| customer_summary | `repeat_customers` | `MAX(repeat_customers_count)` |
| customer_summary | `repeat_share` | `toFloat64(MAX(repeat_customers_count)) / nullIf(MAX(customers_count), 0)` |
| category_sales | `revenue` | `SUM(revenue_amount)` |
| category_sales | `category_share` | `MAX(revenue_share)` — только при группировке по одной category_key |

MAX на summary-полях корректен потому, что по контракту там ровно одна строка. Проверка этого условия обязательна; MAX не должен маскировать несколько версий данных.

Для денег задать отображение двух знаков, для долей формат процентов (`.2%` там, где используется D3-format). Не умножать долю на 100 одновременно с процентным форматированием. SQL-расчёт денежных агрегатов оставлять точным; преобразование к Float допустимо для отображаемых долей и отношений.

## 7. Создание графиков

Для каждого графика: **Charts → + Chart → Dataset → Chart type → Create**. Настроить запрос, выполнить **Update chart**, сверить результат, сохранить в дашборд «Capibara: продажи и покупатели». Названия типов и вкладок зависят от версии Superset.

### Карточки первого ряда

Тип **Big Number** без временного тренда:

1. «Стоимость проданных товаров, без доставки»: order_summary / revenue. Контроль 13 221 498,11. Можно компактно показать 13,22 млн, но точное число должно быть доступно рядом.
2. «Средний чек доставленного заказа»: order_summary / avg_order_value. Контроль 159,88.
3. «Покупатели, все статусы»: customer_summary / customers. Контроль 96 096.
4. «Покупатели с повторным заказом»: customer_summary / repeat_share. Контроль 3,12%; в пояснении указать 2 997 человек.

### Месячная динамика

Создать два расположенных рядом графика из monthly_sales:

- **Time-series Bar Chart**: время `month`, Time grain = Month, метрика revenue, сортировка времени по возрастанию.
- **Time-series Line Chart** или второй Bar Chart: время `month`, метрики delivered_orders и placed_orders с понятными подписями.

Time range поставить **No filter**: нужные 24 месяца уже заданы витриной. Автоматический диапазон вроде Last week даст пустой график на исторических данных. Не включать фильтр revenue > 0, иначе исчезнет ноябрь 2016. Проверить, что ось показывает и пустой месяц.

Не размещать количество заказов и деньги на одной числовой оси.

### Топ-10 продавцов

- Датасет seller_sales, тип **Bar Chart**.
- Категория/group by: seller_id; метрика revenue.
- Горизонтальное расположение, сортировка revenue по убыванию, лимит 10 категорий.
- Лидер должен иметь 226 987,93.
- Рядом сохранить компактную **Table** с seller_id, seller_city, seller_state, orders_count, unit_count, revenue_amount. Raw records mode, сортировка выручки по убыванию, row limit 10. Если доступен только агрегированный режим: группировать по продавцу и его географии, для counts использовать MAX.

Не называть продавца его городом: в одном городе несколько продавцов. Не показывать сумму orders_count по продавцам как общее число заказов.

### Средний заказ

Две небольшие Big Number-карточки из order_summary: avg_lines и avg_units, обе 1,142. Они объясняют гранулярность и полностью закрывают третью задачу вместе с карточкой среднего чека.

### Повторные покупки

Big Number для repeat_customers: 2 997. Рядом короткий текст: «Из 96 096 покупателей 2 997 оформили минимум два заказа. Учитываются все статусы за всю выгрузку». Круговая диаграмма для этого не обязательна.

### Категории

- **Bar Chart** из category_sales: category_label, revenue, горизонтально, сортировка по убыванию, топ-10.
- **Table** со всеми 74 строками: category_key, category_label, revenue_amount, revenue_share. Сортировка по выручке, пагинация, row limit не меньше 74.
- Формат revenue_share — процент с двумя знаками. В Raw records mode это готовая доля; не включать пересчёт Percent contribution для отображаемого топ-10.
- Лидер health_beauty — 1 233 131,72. В таблице должна остаться группа «Категория не указана» и обе категории без перевода.

Отдельная небольшая таблица refresh_status может показывать время обновления в UTC и batch_id. Поле времени не фильтровать историческим периодом продаж.

## 8. Компоновка и фильтры

В **Dashboards → + Dashboard → Edit** добавить сохранённые графики и текстовые блоки:

1. Заголовок и описание правил расчёта.
2. Четыре главные карточки.
3. Два месячных графика.
4. Топ продавцов и топ категорий.
5. Таблица продавцов и полная таблица категорий; можно вынести их на вторую вкладку.
6. Дополнительные показатели заказа и повторных покупок.
7. Дата обновления и ограничения данных.

**В первой версии отключить cross-filtering и не вводить глобальные фильтры.** Summary-таблицы не содержат даты, продавца или категории, поэтому общий фильтр привёл бы к несовместимым показателям на одном экране.

Если фильтры нужны:

- штат продавца — применять только к таблице и графику продавцов; назвать график «Топ-10 в выбранных штатах»;
- категория — только к таблице и графику категорий; доля остаётся долей от всей выручки, это написать в подписи;
- диапазон месяцев — только к месячным графикам, с явным пояснением, что итоговые карточки относятся к полной фиксированной выборке.

Область действия задавать в настройках native filter / Scoping и проверять визуально. При фильтре штата топ-10 должен вычисляться после фильтрации: поэтому seller_sales содержит всех продавцов.

Если позже понадобятся единые интерактивные фильтры, подготовить детальные витрины заказа, позиции и покупателя и заново определить знаменатели. Нельзя просто прикрепить общий фильтр к пяти агрегатам.
