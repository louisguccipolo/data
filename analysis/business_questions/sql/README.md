# Метрики в PostgreSQL DWH

Сборка и тесты только через контейнер:

```bash
docker compose exec -T airflow bash -c 'cd /opt/project/dbt && dbt build --profiles-dir .'
```

Приёмка и проверка детерминизма выполняются полным build по условиям задачи.
Подробности — `.plans/mart-implementation.md`.

SQL 01–10 выполняются в PostgreSQL `dwh` (psql либо SQL Lab с подключением
Marketplace DWH). Контракт колонок — `.plans/superset-guide.md`, §3.1–3.5,
источник `core` в том документе у нас называется `dds`.

Витрины читают `fct_order__active` / `fct_order_item__active`, исключая удалённые записи.
По §20 DDS SK факта ведут к версии на момент первого наблюдения связи (момент продажи).
Если версия на момент привязки неполна или отсутствует, берётся первая полная
версия HK на срезе; иначе сохраняется версия на момент привязки либо первая версия HK.
`seller_sales` агрегирует по постоянному HK продавца и показывает его текущий адрес;
`category_sales` считает продажи по категории версии товара на момент продажи,
а названия — по текущим товарам этого кода, иначе последней версии кода.
История SCD2 хранится в DDS; смена среза требует пересборки DDS и зависимых витрин.

## Определения

- Выручка в BRL — стоимость товаров без доставки у заказов с
  `dim_order_status.is_revenue` (текущая строка статуса); seed задаёт `delivered`.
- Чек включает доставку: сумма `price + freight_value` одного доставленного
  заказа; средний чек — сумма чеков / количество таких заказов. Витрины заказа
  и месяца используют готовые меры DDS `items_price`, `items_freight`,
  `items_value`, `items_count`, не соединяют позиции с платежами или отзывами.
- Одна исходная позиция равна одной единице: `line_count = unit_count`.
  Средние считаются из сумм без промежуточного округления; среднее от цены
  позиции не является средним чеком заказа.
- Покупатель — `customer_unique_id` через `fct_order.customer_sk`,
  повторный — минимум два активных заказа **любого статуса** за всю выгрузку.
  Позиции не присоединяются; заказы без товаров сохраняются. По умолчанию
  Unknown-покупатель не считается личностью, его заказы входят в `orders_count`.
- Только `monthly_sales` ограничена датами покупки `[2016-09-01, 2018-09-01)`:
  24 календарных месяца из `dim_date.month_start`, пропуски → 0.
  `orders_all_count` включает все заказы, `orders_delivered_count` — доходные.
  Остальные витрины охватывают всю выгрузку; срез 2018 в вопросе 09 — только в SQL ответа.
- Категория — исходный `category_code`: пустая = отдельная группа `__unknown__`.
  `category_label` = EN, иначе PT, для неизвестной — «Категория не указана».
  `pc_gamer` и `portateis_cozinha_e_preparadores_de_alimentos` сохраняются
  отдельно без перевода. Флаги в PostgreSQL имеют тип `boolean`.
- `revenue_share` и вычисляемый `repeat_share` — доли 0–1, не проценты;
  процентный формат применяется при показе. Доля категории использует
  выручку **всех** категорий, даже при отображении топ-10.
- `orders_count` по продавцам и категориям неаддитивен; средние и доли
  также нельзя складывать. Summary-витрины содержат по одной строке.

Блок Б реализован по `.plans/mart-spec-vbros-block-b.md`, §2–3. Полные ответы
7–10 и шапка ответа 6 зафиксированы в `.plans/mart-implementation.md`.

- `product_price_history` хранит товар × дата покупки × цена для доходных заказов.
  Смена категории не дробит постоянный товар. Выбор лидера: число цен, единицы,
  затем product_id; дата/цена сортируются только в SQL ответа.
- Штат — `upper(trim(fct_order.customer_state))`, пустой → `__unknown__`.
  Порог 500 в вопросе 7 считается по всем статусам. Доставка и опоздание
  считаются по `is_revenue` с непустой датой доставки, используя меры DDS.
- Воронка включает нулевые статусы и `__unknown__`, знаменатель доли — все заказы.
- Платежи считаются строками, все статусы. `not_defined` — обычная группа,
  нулевая рассрочка входит в среднее и отдельно в `zero_installments_count`.
  Если у активного платежа нет активного заказа, LEFT JOIN сохраняет его
  в Unknown-штате с NULL-годом; суммы обоих полных разрезов остаются сверяемыми.
- Отзыв выбирается по `review_creation_ts DESC NULLS LAST`, затем
  `review_answer_ts DESC NULLS LAST`, затем `review_id DESC`. Один заказ —
  одна оценка, включая отдельную NULL-группу при отсутствии оценки.
  `orders_count` — все статусы, показатели доставки — доставленные с датой.
- Средние — точный numeric без промежуточного округления; доли вычисляются
  из numeric и приводятся к double precision. При нулевом знаменателе — NULL.
  В SQL ответов средние и доли округляются для показа; доли остаются в 0–1.

Тесты `mart_*` проверяют зерно и инварианты с `severity: error`.
Регрессия исходного Olist (`mart_control_*`) имеет `severity: warn`:
новые данные могут изменить контрольные числа и не должны из-за этого
блокировать публикацию. Нарушение инвариантов блокирует сборку.
Текущая месячная выручка равна итогу всей выгрузки, поскольку доходных заказов
вне фиксированного окна сейчас нет; появление таких заказов требует согласовать
окно и обязательный инвариант равенства сумм.
