# Витрины Olist для ноутбуков

Готовые данные находятся в `marts/data/*.parquet`. Первый полный ML-эксперимент —
`notebooks/01_delivery_eta.ipynb` (EDA, CatBoost, бейзлайны, p50/p90 и ночной расчёт пары).
Обзор остальных задач — в `notebooks/train_from_marts.ipynb`.
База данных и Docker для работы не нужны. Правила взяты из `ml-docs/data_marts.md`.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r marts/requirements.txt
.venv/bin/python marts/build.py
.venv/bin/python -m jupyterlab notebooks/train_from_marts.ipynb
```

В текущей рабочей папке окружение `.venv` уже подготовлено. В Jupyter выберите его Python.

```python
from marts import MartStore
store = MartStore()
task = store.task('delivery')
X, y = task.X, task.y
parts = task.split('2018-04-01', '2018-06-01')
# Либо напрямую:
orders = store.read('fct_order_features')
```

| Задача | Таблица | Метка |
|---|---|---|
| `delivery` | `ml_delivery_dataset` | дни от оплаты до получения |
| `review_t0` | `ml_review_dataset_t0` | плохой отзыв, на момент покупки |
| `review_ts` | `ml_review_dataset_ts` | плохой отзыв, на момент опроса |
| `seller_churn` | `ml_seller_churn_dataset` | нет заказов в следующие 60 дней |
| `seller_segmentation` | `ml_seller_segmentation_dataset` | нет, данные для кластеризации |
| `demand` | `ml_demand_dataset` | число заказов на 1–4 недели вперёд |

`manifest.json` содержит параметры, SHA256 исходников, зерно, типы и число строк каждой таблицы,
результаты проверок, перечни признаков, категориальных полей и таргетов.
**Для обучения используйте `task.X`, а не все столбцы таблицы:** рядом с признаками
хранятся метки, бейзлайн и аналитические поля. Пропуски в несглаженных статистиках означают
отсутствие истории; заполнение, кодирование и масштабирование обучаются только на train.
`TaskData.split` делит по времени и убирает из train/valid метки, которые стали известны
после границы соответствующего периода. Для спроса это исключает пересечение окон таргетов.
Не используйте случайное разбиение.

## Слои

- `stg_*`: все 9 очищенных исходных таблиц, тексты отзывов сохранены.
- `dim_geo_zip`, `dim_city`, `dim_calendar`, `dim_calendar_week`, `dim_category_group`: справочники.
- `fct_order_delivery`, `fct_order_features`, `fct_order_review`, `fct_order_at_survey`, `fct_seller_order`: факты.
- `agg_*`: исторические статистики, месячные продажи и недельный спрос.
- `mart_seller_city_features`, `mart_seller_snapshot`, `mart_demand_features`: признаки на дату.
- `ml_*_dataset`: готовые входы моделей.

Исторические агрегаты сохраняются на нужные даты покупки и опроса. Это разреженные
таблицы, не полная сетка всех сущностей на каждый день. Агрегаты пары экспортируются
только при наличии прошлых доставок; итоговая витрина всё равно содержит холодный старт
с нулевыми счётчиками и сглаживанием к родительским уровням.

## Принятые решения

- Время без часового пояса, как в CSV. История использует события строго до начала дня.
  Фактический `snapshot_ts` этих CSV — 2018-10-29 12:27:35 (последний ответ на отзыв),
  а не 2018-10-17 из текста спецификации. Обещанные будущие даты доставки не считаются событиями.
- Повторные отзывы учитываются постепенно: исторический минимум берётся только среди
  уже полученных ответов. Метка заказа — окончательный минимум; её доступность — последний ответ.
- Статистика длительностей доставки исключает противоречивые этапы и неизвестную оплату;
  история отгрузок использует только известные неотрицательные handling/approval.
- Сглаживание `k=10`. Город → штат → платформа; пара → продавец/штат → маршрут → платформа.
- Доставка: покупки `[2017-01-01, 2018-08-15)`, один продавец, положительный известный таргет,
  полные непротиворечивые этапы. Пропуски оплаты и отгрузки в обучение доставки не входят.
- Отзывы: то же окно покупок, включая отменённые и недоставленные заказы с товарами и отзывом.
  Ответы с датой раньше покупки исключаются из исторических признаков; заказы с такими
  метками — из обучения отзывов. В TS также исключены опросы раньше покупки.
  Исходные аномальные записи остаются в `stg_order_reviews`, счётчики — в `manifest.json`.
- Полная история продаж заканчивается **2018-08-30, исключительно**. Редкие покупки сентября–октября
  не считаются периодом отсутствия спроса. Дата всех событий (`snapshot_ts`) считается отдельно.
- Снимки продавцов — 1-е число с апреля 2017 по август 2018. Последняя полноценная метка оттока — июль 2018.
- Для оттока/сегментации `cancel_share_180d` оставлена пустой и исключена из X:
  в Olist нет времени отмены, финальный статус создаёт утечку. Месячные отчёты могут содержать финальные отмены.
- Топ-15 категорий фиксируется по покупкам `[2017-01-01, 2017-04-03)`, до первой точки
  прогноза спроса. Спрос — с 2017-01-02; 102 ряда, включая все нулевые недели.
  Последняя полная неделя — 2018-08-20…26; следующая помечена неполной.
  В `ml_demand_dataset` попадают только точки с четырьмя полными целевыми неделями.
- Показатели отзывов за окно используют последнюю известную дату ответа заказа в этом окне.
  Для нескольких категорий/продавцов отзыв учитывается один раз на сущность.
- `delivery_eta_daily`, `seller_segments`, `demand_forecasts` — результаты ещё не обученных моделей,
  поэтому не заполняются. Опциональные ETA-признаки отзывов пока отсутствуют.
- Полная ночная сетка продавцы × города не создаётся: сейчас нужны обучающие данные.
  `pair_features()` в `src/training.py` собирает признаки тем же способом для переданного списка троек;
  для новых дат историю можно пересчитать через `Histories.at()`.

Границы — воспроизводимые предварительные настройки, а не результат окончательной EDA.
Их можно изменить параметрами `--train-from`, `--train-to`, `--sales-end`,
`--category-fit-to`, `--smoothing-k`. При изменении границы теста зафиксируйте
`category_fit_to` до первой проверяемой точки прогноза.

## Переход на SQL

Код обучения зависит от `MartStore`, имён таблиц и контракта признаков. После реализации
SQL-витрин с теми же столбцами замените только функцию чтения:

```python
store = MartStore(read_table=lambda name: pd.read_sql_table(name, engine, schema='ml_mart'))
task = store.task('delivery')
```

Контракт из `manifest.json` нужно сохранить и версионировать вместе с будущими SQL-витринами.
SQL-источник должен соблюдать те же ключи, типы, границы периодов и доступность событий.

Сборка пишет во временную соседнюю папку `data.building`; публикует `data` только после проверок.
Исходные CSV и существующий ELT не изменяются. Перечни признаков и результаты валидации
можно прочитать без загрузки всех Parquet через `MartStore().manifest`.
